

## 项目概述

**项目名称**：麻将消一消（Mahjong Match-3）

**类型**：单机休闲消除手游

**核心玩法**：经典"上海麻将"类二消——点击两张相同花色且左右不被挡住的牌即可消除，特殊牌含暗牌（需翻面再消除）和吐牌机（消耗次数补充新牌）。底层采用 6 列 × 8 行的棋盘，多层 3D 堆叠（奇数层半格偏移）。

**当前阶段**：MVP 早期，重点是**批量关卡生产工具链**——因为关卡数量需求大（数百关），手工设计不现实。

## Day 12 · 8月5日（周二）：关卡形状生成器 —— 从算法生成转向"模板 + 变体"（关键突破）

### 背景

前几轮尝试纯算法生成关卡形状（v5/v6/v7/v8/v9），始终不满意：要么形状太规整（金字塔、矩形堆叠），要么太乱（随机散点），要么堆叠感不对（全格覆盖 vs 半格覆盖混乱）。今天终于找到正路：**先手工做模板，再用算法做变体**。

### 关键认知（从 real_v2 学到的）

拿到真实官方关卡 `real_v2`（86 张牌、6 层、36→25→15→6→3→1），分析出关键规律：

1. **逐层递减**：从底部（L0）向顶部（L5）逐层减少牌数。越靠近底部牌越多，越靠近顶部牌越少。本层 ≈ 下面一层 × 0.6（即 L0=36 → L1=25 → L2=15 → L3=6 → L4=3 → L5=1）
2. **底层不追求满铺**：左右分坨、有空隙、形状不规则（中间密两边疏）
3. **支撑规则（象限规则）**：上层牌的 4 个象限中心子格 (r,c)(r,c+1)(r+1,c)(r+1,c+1) 每个正下方都要有下层牌——可来自不同下层牌（不能用"单张覆盖 50%"或"必须 2 张托住"，那些是错误结论）
4. **无全覆盖**：上层不能与下层完全重合（遮挡隐藏下层牌）
5. **严格左右对称**：row ↔ -row（row=0 中轴牌镜像到自身，允许单张）
6. **自由偏移**：底层整格，上层可错位半格（不强制整格/半格层交替）

### 形状编辑器（自研）

为了手工做模板，写了一个 HTML 关卡形状编辑器 `shape_editor.html`：
- **坐标系**：row=横（-5..5），col=纵（-8..6），每张牌占 2×2 子格，左上角 (row=-5,col=-8)
- 分层编辑（Q/E 切层），每层颜色不同
- 对称绘制开关（画左边自动镜像右边，row ↔ -row）
- 支撑限制（上层只能在有支撑的位置放，红叉提示）
- 悬空检查（象限规则：4 个象限中心子格下方都要有牌）
- 三种画笔：普通牌、暗牌、吐牌机（含方向、次数）
- 导入/导出 JSON 与编辑器格式兼容
- 坐标显示开关（牌面显示 row,col）
- 俯视视图，上层牌向上偏移露出下层（能看出叠层关系）

### 突破：模板 + 变体（v10）

方案：**手工准备一批模板（真实关卡样式）→ 用变体生成器批量产出**。

变体机制（`shape_generator_v10.js`）：
- **平移**：整体上下移动
- **挖洞**：随机去掉几对（被上层依赖的牌不能挖，保持支撑）
- **加牌**：合法位置补几对
- **删层**：随机去掉最高层

结果：20/20 变体全部通过校验，保留了模板的"真实手感"，但每关都有细节差异。**最终确认可行**。

### 填花色方案研究：倒推法（Backward Generation）

形状问题解决后，研究怎么给布局填花色（typeId）。对比两个方案：

**方案 A：随机填 + 解算器验证**（`level_generator_demo_v3.js` 已实现）
- 随机分配花色，用 DFS 解算器验证可解性，不可解就重试
- 缺点：成功率低（大布局常试几十次才中一次）、不可控

**方案 B：倒推法（推荐）**
- 从空棋盘开始，模拟"消除的逆过程"：随机选一个当前可见（未被更高层挡住）的位置，放一对同花色牌上去
- 每放一对，新牌可能盖住之前放的牌 -> 棋盘逐渐变满，深层牌自然产生
- 因为是消除过程的倒放，最终布局 **100% 可解**，且深度自然产生（不需要人为设定"先放深层再放表层"）

**关键澄清**：倒推法不是"从顶层往下"填（那样正着玩会一路直接消下去，太简单），而是"随机挑当前可见的位置"填。随着牌越放越多，后放的牌会盖住先放的，形成表层/深层的差异。

**深度差异的成因**：同一对牌 A1/A2 在倒推时同时放置，但位置不同。A1 放边缘后续少被盖 -> 保持可见；A2 放中央后续多次被盖 -> 深埋。正着玩时玩家看到 A1，必须先消掉压在 A2 上的牌才能匹配--这正是真实关卡里的"钩子"结构。

**钩子偏置**：纯随机倒推的"钩子"是概率出现的。要让每关稳定有几个"A1 可见 / A2 深埋"的钩子，需要在倒推时加引导：少数几对牌故意拆到边缘和中央，其他对正常随机。

**难度量化方向**：
- 初始可点率（越低越难）、层数、平均选择数（每步可选花色数，越少越难）、牌数
- 倒推时可直接控制生成顺序来设定难度（先放表层牌多 = 简单，先放深层牌多 = 难），难度是"设计出来的"而非事后评估

### 下一步

1. 用户继续提供更多"底子"模板（不同 L0 形状）
2. 每个模板用 v14 规则生成器产出 20+ 变体 → 几百关
3. 接倒推法填花色 + 难度评分（level_generator_demo_v3.js 已验证可用）
4. 特殊牌（暗牌、吐牌机）在编辑器中摆放

### 心得

- **纯算法生成"有设计感"的形状极其困难**，因为好看的形状本质是"手摆的"——有语义、有意图
- **"模板底子 + 规则生成"是最终方案**：用户提供不同 L0 底子（摆方块规则），算法按规则生成上层散落形状（v14）
- **变体不能只是"微调模板"**（v11 挖洞/加牌/平移变化太弱），要**按规则重新生成上层**（v14 8 种散落风格）
- **支撑规则是"象限规则"**（4 个象限中心子格下方都要有牌），不是"4/4 全覆盖+2 张托住"（那是错误结论，real_v2 大量牌只有 1 张托住）
- 生成器、校验器、编辑器三处规则必须一致，否则会出现"生成器说行、编辑器说悬空"的冲突
- 坐标系 row=横/col=纵 容易搞混，导入导出要往返测试（导出→导入→对比）确认

## Day 12 再补充 · 8月5日：V17 随机生成器定稿（放弃"风格命名"）

### 背景

v14 的 8 种"散落风格"批量产出的关卡，用户始终不满意：要么太稀疏（上层牌太少），要么太规律（对称方块），要么偏置风格把塔拆散。反复试 v15（有序密排太方块）、v16（删对称/全覆盖规则——**严重错误，违反既定规则，被否决**）之后，最终定位到根本问题。

### 关键认知

1. **"偏置风格"（左偏/右偏）这个设计本身就是错的**。真实麻将塔是"一个整体"：最宽在底、一层层收窄、最后收成一个尖（L5=1 张），所有层在同一条中轴上。左偏/右偏把上层限制到半张棋盘，结果就是"一大片底 + 角落一坨"，视觉上断裂，永远不像真关卡。
2. **读 real_v2 底层坐标发现：L0 根本不是实心矩形**，而是有形的"底子"——左边缘一列 6 张、中间块 12 张、右侧厚块 18 张，左薄右厚、有缺口。这才让关卡看起来像真的。生成时保留 L0 原样就是保留这个"底子"。
3. **上层要立得住，L1 必须"有序互锁"**（棋盘式密排，像骨架，喂饱上层）；L2 及以上才能"随机有机"（打乱挑选）。如果 L1 就随机，上层会因支撑位不足级联塌陷。
4. **淘汰"风格命名"**：不再有"均匀散落/中央密集/横条"这些标签。每次生成时随机抽取金字塔目标（L1 基础 13 张，往上递减，每层加 0.7~1.3 随机抖动）和行偏好（从中抽 1~3 行作排序优先），结果天然每关不同、又都保持中心塔。

### V17 生成方案（定稿）

**整体思路**：L0 用模板原样（保住"底子"形），L1 有序互锁（撑起塔的骨架），L2~L5 随机有机（制造每关差异）。无风格命名、无偏置，始终中心化。

```
L0       = 模板 real_v2 的底层（36 张，原样保留）
L1       = ordered 有序密排（互锁骨架，够密）
L2..L5   = random 随机有机
每层张数   = 随机金字塔目标 × 随机抖动
```

**具体机制（从 shape_generator_v17.js 提炼）**：

1. **每层张数**：基础目标 `baseTargets = [13, 9, 6, 4, 2]`（对应 L1..L5，镜像展开前）。每层实际张数 = `基础 × 随机抖动(0.7~1.3)`，下限 2。所以最终分布约 `36 / 20~28 / 11~18 / 4~9 / 1~4 / 0~2`。

2. **行偏好**：每次从 `[1, 3, 5]`（棋盘中间三行）随机抽 1~3 行，作为该关的"优先行"。行偏好**只影响排序**（先填哪行），**不排除其他行**——保证塔始终占满中轴、不会偏到一边。

3. **候选位置**：遍历 `row 0..5, col -8..6`，保留**被下层完全托住**（象限规则：4 个象限中心子格下方都有下层牌）且**不越界、不与下层同格重合**（无全覆盖）的位置。

4. **L1 ordered 模式**：按"优先行 → 行 → 列"有序密排，尽量挑不互相重叠（2×2 不相交）的位置。这样 L1 形成互锁的密集骨架，为上层提供充足支撑位。

5. **L2+ random 模式**：候选打乱后随机挑，同样保证不互相重叠。有机散落，每关不同。

6. **镜像展开**：选中位置 `(row, col)` 后，自动补上镜像位 `(-row, col)`（左右对称规则）。row=0 中轴牌镜像到自身，允许单张。预选数因此约 ×2 得最终张数。若展开后超出上限则随机裁剪。

7. **兜底**：最后剔除缺下层支撑的牌（含其镜像），保证无悬浮牌。

8. **校验**：每关过完整规则——严格左右对称 / 象限支撑 / 无全覆盖 / 同层不冲突，24/24 通过。

### 结果

一次生成 24 关，24/24 全部通过完整校验（严格左右对称 / 象限支撑 / 无全覆盖 / 同层不冲突）。分布健康：底部 36 → L1 18~28 → 逐层收窄到尖，大部分是 6 层实芯塔，少数（如 L015/L017）顶部收得陡（L4/L5 塌到 0）。用户确认：**"就按这个算法来生成，后面出问题再说"**——算法定稿。

- `outputs/关卡配置/shape_generator_v17.js` — 随机生成器（定稿）
- `outputs/关卡配置/batch_generate_v17.js` — 批量脚本（PER_TEMPLATE 可调）
- `outputs/关卡配置/batch_v17/` — 24 关（JSON + 预览 txt + 汇总）
- v14~v16 生成器保留作参考（已废弃）

## Day 13 · 8月6日（周三）：倒推法填花色 + 横纵轴规则统一 + 难度量化

### 一、倒推法填花色（backward_fill_v17.js，100% 可解）

形状定稿后，用**倒推法**给布局填 typeId（花色）：

- **34 种花色**：万1-9 / 条1-9 / 筒1-9 / 东南西北中发白
- **每种随机 0~3 对（不要求全出现）**：某个万字可能 0 次、另一个万字却出现 3 次——这是难度来源之一
- **倒推法本质 = 正向模拟消除**（不是真的"倒着放"）：
  1. 每步从当前**可点**牌里随机挑 2 张当作一对
  2. 用游戏原生的 `isClickable` 直接判定（被更高层压住 / 被同层左右夹住即不可点）
  3. 记录这对并移除
  4. 移除只会让更多牌变可点（可点集只增、不减少）→ 配对必然走到终点
  5. 放牌顺序的**逆序**就是合法消除序列 → **100% 可解**
- **钩子自然产生**：随机挑对，天然出现"一对里一张早暴露、一张深埋"（layer 差 ≥ 2），正是真实关卡的钩子结构
- **校验白证**：用 `verifyByElimination` 按消除序列正推一遍，每步两张同花色且可点，跑到底清空

### 二、横纵轴规则统一（本次踩的坑，已修复）

**背景**：此前把 `game_demo.html` 的横纵坐标交换过（row=横/col=纵）。交换后 demo 的 `isClickable` 已改为 `row ± 2` 判"左右夹住"（正确）。

**问题**：但生成器 `backward_fill_v17.js`（和旧方案 `color_fill.js`）的 `isClickable` 仍用 `col ± 2` 判"左右"——在 row=横/col=纵 的约定下，`col±2` 实际是**上下**夹住，不是左右。**生成器和游戏 demo 的可点规则不一致**：

- demo（正确）：被**左右**夹住不可点 → 判 `row ± 2`
- 生成器（错误）：用 `col ± 2` 当左右 → 实际判的是**上下**夹住

**后果**：生成器用错误轴保证可解，demo 用正确轴玩。有些对（一个 L0、一个高层）在生成器看来可同时消，真实规则下其中一张被左右夹住、永远点不到 → **"两个都无法消除"**。

**实测**：用正确规则求解，24 关里 **6 关不可解**（含 demo 默认加载的 level_001）。

**修复**：
1. `backward_fill_v17.js` 的 `isClickable` 左右判定改为 `row ± 2`（same col）
2. 重新填色：24/24 成功
3. 用正确规则重新求解校验：**24/24 全部可解**（之前 6 关不可解）
4. 顺带修 `color_fill.js` 的 `isHorizNeighbor` 和 `isClickable`（同 bug）

**教训（重要）**：生成器 / 校验器 / 游戏 demo 三处 `isClickable` 必须**同轴**。坐标一旦交换，必须把三处一起改，并往返核对（生成出的板子用游戏规则重跑求解器）。

### 三、难度量化

**公式**（`evaluateDifficulty`）：

```
难度分 = (1 - 可点率) × 40  +  层数 × 8  +  min(钩子占比, 1) × 30  +  10     （clamp [0,100]）
```

- **可点率** = 初始可点牌数 ÷ 总牌数（越低越难）
- **层数** = 最高层索引 + 1（每层 8 分）
- **钩子** = 一对中两张 layer 差 ≥ 2 的牌对数（占比超 1% 吃满 30 分）
- **基础** +10

**实测（24 关，原始分）**：最小 67 / 最大 117 / 平均 102.3。

**⚠️ 发现公式饱和、区分度不足**：
- 层数项 ×8 主导（6 层就 48 分）；钩子项按"占比饱和"太容易吃满
- 结果：凡 6 层、可点率低、有钩子的关，原始分普遍 >100（clamp 后全 100），**排不开难度**
- 待改进方向：① 降低层数权重 / 用对数压层数；② 钩子改按数量线性积分而非占比饱和；③ 引入解算器 DFS 搜索量（节点数）作为更细的难度指标

## Day 13 补充 · 8月6日：消除逻辑修复 + 输出命名与难度落地

### 四、消除逻辑 bug 修复（按牌 id 而非按花色）

**现象**：消掉 L0 的两张「四万」后，L4 相邻的两张「四万」也同步消失了。

**根因**：`checkMatch` 用 `matchedTypeIds`（按**花色/typeId**）记录"已消除"，匹配 2 张就把整个花色判为已消除；`getActiveTiles()` 按花色过滤，于是同花色其余牌（比如另一种子出 2 对的、共 4 张的花色）被一并剔除。

**修复**：改为按**具体牌 id** 记录（`matchedTypeIds` → `matchedTileIds`），匹配时只把进卡槽那 2 张的 id 记录为已消除，同花色其他牌不受影响。

**关联**：这个 bug 与"两个无法消除"（生成器轴错）是同一套"按花色 vs 按牌"语义的两面——之前按花色记录导致**少消不掉**，这次按花色记录导致**多消**。都已回归"按具体牌"。

### 五、输出文件命名落地（real_v2 → T1 + 难度分）

- 填色成品不再沿用源模板名 `level_XXX_real_v2_随机.json`，改为 **`level_XXX_T1_<难度分>.json`**
- **T1**：用户第一张"只给第一层（L0 底子）"的模板代号（曾暂用 V1，因与生成器 v1~v17 版本号冲突，改 T1 消除歧义）
- 难度分取自 `evaluateDifficulty`
- 实现：`backward_fill_v17.js` 的 `outFilename()`（`BATCH_TAG` 常量，可改），写盘前算难度拼进文件名
- 填色是**确定性**的（RNG 种子由源文件名数字决定），改命名重跑内容不变

### 六、难度去上限（原始分）

- 原公式 `Math.min(100, ...)` 有 0-100 上限，导致大半关卡原始分 >100 被压成 100，文件名里排不开难度

## Day 14 补充 · 8月6日：std 标准坐标全链路（生成新文件，原脚本不动）

### 背景

老板的 Unity 关卡用的是 **row=上下(纵)、col=左右(横)** 的"标准"坐标，而我们内部工具链是 **row=横/col=纵**。此前做了隔离的导出转换脚本（`export_to_unity.js`，只交换导出值）。用户决定干脆**把整条工具链翻成新文件**，统一成标准坐标，但**不碰原来成功的脚本**。

### 方案：翻成新文件（_std 后缀）

| 新文件 | 改了什么 |
|--------|----------|
| `shape_generator_v17_std.js` | 算法内部仍用 row=横/col=纵 运算，只在 `toEditorJSON` 导出处交换 row/col 值 |

## Day 15 · 8月10日（周日）：简化版程序文档重写 + 分数公式与 Combo 规则定稿

### 背景

| 章节 | 内容 | 格式 |
|---|---|---|
| 1. 功能描述 | 一句话说明这个功能干什么 | 正文段落 |

| 5. 验收标准 | 什么时候算完成 | √ 标记 |

**格式要求**：标题四号黑体加粗，正文小四宋体，全黑。

### 产出

- `outputs/需求表/简化程序文档/PROG-0100.docx ~ PROG-0501.docx` — 共 **35 份** Word 文档
- 覆盖：主菜单（5）、局内游戏（19）、结算界面（3）、系统后台（3）、排行榜（2）
- 生成脚本：`outputs/需求表/_gen_simple_docs_docx.cjs`（数据 + 渲染一体，便于后续批量修改）

### 分数公式定稿（PROG-0202）

之前草稿写的是「基础分 320 + Combo × 40」的线性加法，感知不强。改为**倍率制**：

```
单次消除得分 = 基础分 × Combo 倍率
```

| Combo | 倍率 | 单次得分 |
|---|---|---|
| 1 | ×1 | 100 分 |
| 2 | ×1.5 | 150 分 |
| 3 | ×2 | 200 分 |
| 4 | ×2.5 | 250 分 |
| 5 | ×3 | 300 分 |
| 6 | ×3.5 | 350 分 |
| 7 | ×4 | 400 分 |
| 8+ | ×4.5 | 450 分（封顶） |

- 基础分 100（整数好记，分数干净）
- 8 连封顶 ×4.5（防止数值爆炸）
- 估算单局总分：正常通关 5000~8000，高手 12000~15000

### Combo 中断规则修正（重要）

之前草稿写的是「入槽不消除 = Combo 中断」，讨论后修正为：

- **Combo 清零（中断）**：玩家点击到**锁定牌**（被压住 / 被左右夹住的不可操作牌）—— 这是操作失误
- **Combo 保持不变**：入槽但没配对消除 —— 正常选牌，不算失误
- **Combo 保持不变**：使用道具（洗牌/提示/撤销）

同步更新了 PROG-0202（分数显示）和 PROG-0221（Combo 连击激励）两份文档的特殊规则和验收标准。

### 心得

- **简化文档的核心是"砍掉铺垫"**：概述、玩家场景、触发前置这些章节信息其实都能合并进逻辑流程和特殊规则里。5 章结构比 7 章少了 30% 的文字量，但关键信息一点没丢。
- **Combo 中断的定义一定要在文档里写死**：「什么叫失误」直接影响分数和爽感，程序、策划、测试三方必须对同一句话，不然后面扯皮。定义成"点到锁定牌"是最清晰的——玩家犯错就惩罚，正常选牌不惩罚，手感上也更宽容。


## Day 13 补充 · 8月6日：std 坐标全链路（row=上下/纵, col=左右/横）

### 背景

老板的 Unity 关卡用的坐标是 **row=第几列/纵向、col=第几行/横向**（即 row=上下、col=左右），和我们内部 **row=横向/col=纵向** 正好相反。之前已做过一版"仅导出转换"（`export_to_unity.js`，isolated，低风险）。但用户决定**干脆把整条工具链统一成标准坐标**，于是新增一套 `_std` 文件，**原脚本一字不动**。

### 方案：新增一套 *_std 文件，原脚本保持成功

内部算法全部不动，只在**坐标边界**交换，风险最低：

| 文件 | 改动点 |
|------|--------|
| `shape_generator_v17_std.js` | 与 v17 相同算法；仅在 `toEditorJSON` 导出处把每张牌的 row/col 值互换 |
| `batch_generate_v17_std.js` | 指向 std 生成器，输出到 `batch_v17_std/` |
| `backward_fill_v17_std.js` | 与 v17 相同；仅 `isClickable` 左右夹轴从 row 改为 col（std 里左右=col±2） |
| `shape_editor_std.html` | 关键发现：编辑器**内部本来就是 row=纵/col=横**，原来在 JSON 接口处交换。std 版直接去掉交换，JSON 与内部一致 |
| `game_demo_std.html` | 渲染 x←col、y←row；`isClickable` 左右夹轴 col±2；默认加载 std 关卡 |

### 内部坐标约定差异（容易踩坑）

- **生成器/填色内部**仍是 row=横（-5..5）、col=纵（-8..6），只在导出时交换
- **编辑器内部**本来就是 row=纵、col=横 —— 与 std 目标一致，所以 std 版只是"不再交换"
- **std 成品 JSON**：row=纵（-8..6，上负下正）、col=横（-5..5，左负右正）

### 验证结果

- 生成 24 关 → 填色 24/24 成功、**24/24 校验可解**（白证）
- 坐标方向实测：row=-8 渲染在顶、row=4 在底（row=纵 ✓）；col=-5 在左、col=5 在右（col=横 ✓）
- 可点判定：被左右(col±2)夹住的牌不可点 ✓；正常消除 82→80 ✓
- 编辑器往返：读 std JSON 层数 [36,22,15,7,2] 一致；导出 82 张 0 缺失 0 多余 ✓

### 产出文件

- `outputs/关卡配置/shape_generator_v17_std.js` / `batch_generate_v17_std.js` / `backward_fill_v17_std.js`
- `outputs/关卡配置/shape_editor_std.html` / 根目录 `game_demo_std.html`
- `outputs/关卡配置/batch_v17_std/`（24 关形状）/ `batch_v17_std_填色/`（24 关成品，T1+难度命名）
- 原 v17 脚本、编辑器、`game_demo.html`、`export_to_unity.js` 全部保持不动

### 心得

- **"翻坐标"最省事的位置是坐标边界**：算法内部用哪套都行，只要 JSON 进出统一。生成器在导出交换、填色在判定交换、编辑器干脆内部就是目标约定，三处思路不同但结果一致。

## Day 15 · 8月11日（周一）：暗牌机制 + T2 模板链路 + 全面清理

### 一、暗牌机制（新玩法落地）

决定做**暗牌**玩法：填色完成后随机挑几张牌标为暗牌（`specialTiles`，`type:'dark'`），玩家看不到牌面、需翻面才能匹配。**关键设计**：

- **暗牌只隐藏牌面，不改变"哪些牌可点、消除序列成立"** → 任意暗牌数量下关卡仍 100% 可解，倒推填色逻辑零改动
- **优先把"钩子对里深埋的那张"标暗**（layer 差 ≥ 2 对里更深的那张 = 被盖住/夹住、看不到是什么的那张）——这是暗牌最能加难度的场景
- **难度公式加权**：新增 `暗钩子占比 × 20` 项

```
难度分 = (1-可点率)×40 + 层数×8 + min(钩子占比,1)×30 + 暗钩子占比×20 + 10
```

**产出**：`backward_fill_v17_std_dark.js`（T1 用，输出 `batch_v17_std_填色_暗牌/`，24 关，实测每关 100% 含暗钩子，平均难度 103→123.7）。

### 二、T2 模板链路（新模板 T2_gong）

用户手工摆了个新 L0 模板 `模板/T2_gong.json`（std 坐标，44 张，仅 L0），要求生成 `level_001_T2_xxx.json` 到 `T2_暗/`。配了专用脚本：

- `batch_generate_T2.js` — 用 T2_gong 生成形状 → `batch_T2/`
- `backward_fill_T2_dark.js` — T2 暗牌填色（BATCH_TAG='T2'）→ `T2_暗/`

**踩了两个坑（都修了）：**

1. **std 模板坐标不匹配**：T2_gong 是 std 编辑器摆的（row=纵/col=横），生成器内部用 row=横/col=纵，只在导出时交换。直接喂 → 模板 L0 被当内部坐标，对称校验全挂（row=-8 镜像到越界）。修法：T2 批量脚本加载模板时先把坐标 std→内部对调，生成完再换回 std。

**结果**：24 关，24/24 可解，6 层塔，难度 62~136，命名 `level_001_T2_114.json` 这种，坐标 std（row=-8..6 纵 / col=-5..5 横）。

1. **CSS 改造**：`.tile` 从「象牙白+彩色符号的牌身」退化成纯定位/投影容器，里面只放 `<img class="tile-img">` 用 `object-fit: contain` 居中显示真实图。`.tile.dark` 删掉（暗牌直接用背面图当 src）。`.slot .slot-tile` 同样换成 img 容器。层号 L 徽标保留。选中高亮从 `outline` 改成 `drop-shadow`（贴合 PNG 透明圆角的剪影）。
2. **JS 改造**（`game_demo_std.html`）：
   - 新增 `shuffleArray(arr)` Fisher-Yates、`buildTypeImgMap()` 会话内只洗一次、`tileImgSrc(typeId)` 取图（带兜底）
   - `render()` 给每张牌 `<img src="${isBack ? TILE_BACK_IMAGE : tileImgSrc(t.typeId)}">`；`renderSlots()` 同款
   - `init()` 顶部加 `buildTypeImgMap()`；`parseTypeName` 删除（不再需要）
3. **构建注入**：写 `inject_tiles.js` 把 47 张 PNG 读成 base64，替换源码里的 `/*__TILE_DATA__*/` 占位 → 输出 `const TILE_FRONT_IMAGES=[45] / TILE_BACK_IMAGE / TILE_BLANK_IMAGE`。HTML 约 6.5 MB，单文件、双击即玩。
4. **两个坑**：
   - marker 原来嵌在 `// ...处（...）。` 注释行尾，第一次注入后 `const TILE_FRONT_IMAGES = [` 被 `//` 吞了，解析成裸 array literal → `TILE_FRONT_IMAGES is not defined`（浏览器静默、看上去就是全局变量没定义）
   - marker 行尾的 `。` 残留在 `const TILE_BLANK_IMAGE = "...";` 之后，V8 直接 SyntaxError
   修法：把 `// 注释` 和 `const ... = [` 拆两行；删掉 stray `。`。验证手段：node `--check` 抽内联 script。

### 随机映射设计

- 页面打开时洗一次（Fisher-Yates）→ typeId 0..32 各分一张不同图（45 张够，34 张富余）
- `白`（typeId 33）固定 → 白板图
- 同会话内点「重来」/导入关卡 → 映射不变（玩家一关内不会看到同一 typeId 突然变脸）
- 重开页面 → 重新洗（保证每次有新体验）

- 98 张牌全显、object-fit: contain、L 徽标到位
- 11 张暗牌全部显示背面图，点 clickable 暗牌 → 翻面并选中（data-dark=0）、点第二次 → 入槽（槽内也是正面图）
- 「重来」前后 `typeImgMap` 序列化结果相同 → 映射稳定
- 控制台 0 报错

- `outputs/游戏Demo/game_demo_std.html` — 改后版本（6.5 MB，图片全 base64 内嵌）
- `游戏Demo说明.md` — 第二节牌面样式段已同步改写
- 工具：临时构建脚本留在 `AppData/Local/Temp/tilecheck/inject_tiles.js`（不交付）

### 心得

- **嵌入 base64 的 marker 行最容易踩注释的坑**：未来类似注入要么 marker 单独成行、要么用更独特的不可被注释吞的格式（如 `/*@@INJECT@@*/` block）

## Day 17 又补充 · 8月16日：空白块修复 + 按钮改名 + 批量生成

## Day 17 又补充2 · 8月16日：探测分数 + 不对称底座 + 生成流程重构

### 一、探测本底座可出分数（📊）

用户说"不知道分数的上下限" → 加「📊 探测本底座可出分数」按钮：对当前底座生成 20 个样本，显示 **最低 / 最高 / 平均分**，并**自动填入目标分数输入框**。实测 10 张底座：最低 69 / 最高 126 / 平均 106。

### 二、不对称底座支持（去掉硬性对称要求）

用户放九宫格报 `[对称] L0(3,-5)` → 生成器要求底座左右对称（镜像塔是游戏惯例），但用户觉得没必要。改：

- `generateFromTemplate` 加 `mirror` 选项：`mirror=false` 时 `generateLayer`/`expandMirrorWithLimit` 不做镜像展开
- `validateShape` 加 `skipSymmetry` 选项
- `generateStackFromShape` **自动检测底座对称性**：对称 → 正常镜像堆塔；不对称 → 关镜像 + 跳过对称校验，按实际形状堆
- 踩坑：不对称时层不镜像翻倍，**总牌数可能变奇数** → 生成后从顶层删一张凑偶（`toEditorJSON` 的奇数处理对不对称形状无效，因为它找"轴上牌"或镜像对，不对称时找不到）
- 九宫格（9 张）是**奇数**，二消无法配对 → 明确报错"底座是 9 张（奇数），请加/删一张"（数学硬约束，不是 bug）
- 实测：不对称 12 张底座 → 成功生成 14 张可玩关卡（44 分）✅

### 三、生成流程重构（常驻结果列表 + 批量模式）

用户两点不满：
1. **"批量生成到底按形状还是按底座？没规范"** → 加 **批量模式下拉框**（按底座堆塔 / 按当前形状），和"数量""分数"一起明确
2. **"点预览弹窗就关了，其他结果看不到"** → 弹窗改成**右侧面板常驻的「📋 生成结果」列表**：
   - 批量生成的**所有结果**都在列表里，每行 `#n 分数 张/对 层 暗` + 预览/下载
   - 点某行预览 → iframe 加载，**列表不关**，来回切换
   - 单个生成也进列表（生成 1 个 = 列表 1 项 + 自动预览），当前预览行红色高亮
   - 顶部「⬇ 下载全部」「清空」

最终生成规范：**形状来源（当前形状/底座堆塔）× 数量（单个/批量）× 分数（单个不控，批量可设）**。

### 四、Git Bash 连不上 GitHub 的解法（重要）

问题：Git Bash 的 git **不走系统代理**，即使浏览器/梯子开着也 `Could not connect to github.com:443`。用户终端能推是因为它走了代理。

发现：本机梯子监听 **127.0.0.1:7897**（Clash 系默认）。验证方法：
```bash
for p in 7890 7897 10809 1080 8888 10808 2080; do
  timeout 3 curl -s -o /dev/null -w "port $p: %{http_code}\n" --proxy http://127.0.0.1:$p https://github.com
done
```

```bash
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push
```
可以永久配置（一次性写入，以后免带 flag）：
```bash
git config --global http.proxy http://127.0.0.1:7897
git config --global https.proxy http://127.0.0.1:7897
```

### 心得

- **"对称"是设计约定不是游戏约束**：镜像塔好看、且镜像层天然偶数（配合二消），但它不该成为挡用户的门槛。让工具自动检测、能对称就对称、不能就按实际来，比报错强。
- **奇数张是数学硬约束**：二消 9 张永远有一张落单。这类约束要给用户**能行动的提示**（加一张/删一张），而不是干巴巴报错。

### 五、难度公式 v2：钩子从"有/无开关"改为按数量计分（本次核心）

**问题发现过程**：用户连续追问"同一底座探测分数为什么每次不一样""钩子是什么""1 个钩子和 30 个钩子真的同分吗"，逐步挖出 v1 的结构性缺陷：

- v1 公式 `min(钩子数/总牌数×100, 1) × 30`：百来张牌时只要有 1 个钩子占比就 >1、直接拿满 30 分——**钩子项二值化**，1 个钩子和满盘钩同分
- 三重验证确认：① 公式反算之前批量生成的两关（123/121 分）逐位吻合；② 现场生成 6 关，1 个和 2 个钩子都拿 30 满分；③ 文档第六节自己承认"钩子/暗钩子易触顶"
- 顺带查清**探测分数波动的真正主因**：不是花色，而是堆塔本身随机（每层张数 0.7~1.3 抖动 + L2+ 随机布局），同底座每次塔形都不同，可点率随之波动
- 花色分布也确认了：倒推法随机分配、每花色上限 3 对，34 对摊 34 花色是生日悖论（全一对概率约 10 万亿分之一），典型分布约 12 种空缺/12 种一对/7 种两对/2 种三对

**v2 修改**（三处副本一次改齐：浏览器 generator.js / Node generate_fill_std.js / 仓库 editor/generator.js）：

```
钩子项：   min(钩子数 / 5, 1) × 30    每 1 个钩子 +6 分，5 个拿满
暗钩子项： min(暗钩子数 / 5, 1) × 20  每 1 个暗钩子 +4 分，5 个拿满
```

- 分母 5 是实测校准：80~110 张常规关卡钩子数观测 0~5 个（中位 2），5 个封顶正好覆盖
- **新旧对比实测**（同底座）：旧公式 1~5 个钩子全部挤在 121~127 分；新公式拉开为 86/97/106/116/121，每个钩子约 10 分台阶（钩 6 + 暗钩 4）；0 个钩子和 5 个钩子的关分数不变
- **v1 与 v2 分数不可混排**，旧批次需整批重新生成；《难度分说明.md》全文重写为 v2 版，《使用说明.md》公式段同步

### 四、堆塔对称性 bug 修复（6×8 底座报错）

**现象**：对称底座 + 按底座生成 -> 约 20-30% 概率报「堆层校验失败: [对称] L4(x,y)」

**排查过程**（完整走了一遍死胡同才找到）：
1. 先怀疑校验和底座检测轴向不一致（std col-mirror vs internal row-mirror）-> 改了三处，反而更糟
2. 用 Node VM 直跑生成器（绕过浏览器缓存）复现 -> 确认是真 bug 不是缓存
3. 逐步排除法：直接调 `generateFromTemplate` + `validateShape` **0 失败** -> 缺口在 `generateStackFromShape` 独有的逻辑
4. **根因**：奇数张时的"删顶层一张凑偶"逻辑（第 660 行）删的是**任意一张**，破坏镜像对称。删掉 A 但留着 A 的镜像 B -> B 缺对称伙伴 -> 校验失败
5. **修法**：奇数时成对删除（一张 + 它的镜像对称牌）；顶层找不到镜像对则删中轴线上的牌（row=0，自身对称）

**验证**：100 次生成 0 失败（修复前 5-10 次/30 失败）

### 一、难度权重校准测试方案 → 搁置（重要决策）

**背景**：用户要求出一份"每个维度单独拉满、测通关时间、反推权重"的测试方案。方案已生成(docx)后,用户反思测试可行性,连续提出两个关键质疑:

1. **"一个维度拉到极端后,其他维度设多少?"** → 理论上设最低值才能隔离,但生成器维度之间**相关**(层数拉满 → 钩子自然变多),做不到完全独立
2. **"生成 3 关测通关时间,能算权重吗?"** → 诚实答案:只能给粗略排序,给不了精确权重;3 关样本太小,维度相关性会淹没信号

**决策**: 放弃一步到位的权重测量,**搁置为待执行项目**。三个备选路径留给未来:
- **A. 大样本**:每维度 5-8 关 × 5+ 人,回归分析(最准但最费工)
- **B. 粗略初版 + 上线迭代**:每维度 3 关 × 2-3 人定初版,上线后据玩家数据持续调(当前最务实)
- **C. 设计判断 + 小规模验证**:凭机制分析定权重,5-6 关验证"公式分排序 ≈ 实际难度排序"

**暂定走 B**:先用当前权重(钩 30 / 暗钩 20 / 可点 40 / 层 8)作为初版,上线后用"难度分 vs 最佳通关时间"的相关性做后续校准。试玩计时闭环已就绪,只差数据积累。

### 二、生成参数合理性复盘(核心问题)

**用户提出的关键问题**:"给定底板后设钩子=5、暗钩=5,但实际没这么多牌可摆,怎么办?目标数是否该改成百分比?"

**分析**:
- 钩子产生条件:同一花色一对牌层差 ≥ 2
- **硬约束(形状)**:扁平底板(所有牌在 L0/L1)层差最大为 1 → 钩子恒等于 0,设多少目标都没用
- **软约束(花色分配)**:backwardFill 随机分配,钩子数范围有限
- 当前处理:重试 30 次达不到就认输返回最后一次 → 出现"目标钩 5 实际钩 2"

**百分比方案的评估**:
- ✅ 解决规模适配:30 张和 110 张底板,50% 自动缩放数量
- ❌ 不解决结构不可能:扁平底板 0% 之外的任何目标都不可达

**决定方案:百分比 + 尽力匹配**:
1. 钩子/暗钩目标从绝对数(0~10)改成百分比(0~100%,占"总对子数"比例)
2. 容差 `TOL_HOOKS` 从绝对值 ±1 改成相对值 ±10%
3. 生成逻辑从"达到才停"改成"重试 N 次后取最优",清晰展示偏差
4. 现有 `structCompareText` 已能显示"钩5(+2)"这类偏差,只需改目标语义

**已实施**(用户确认后完成):
- `generator.js`:`evaluateDifficulty` 加入稀缺度加权 `effHooks = Σ(钩子实例数 / 该花色对子数)`,独占型钩子满分、泛滥型钩子打折;新增 `effHooks`/`effDarkHooks`/`totalPairs`/`hookDensity`/`darkHookDensity` 字段
- `index.html`:(a) 钩子/暗钩滑轮从绝对数改百分比 0~100%(默认 30%/20%);(b) 删掉可点旋钮(随机生成自然体现);(c) 容差改 ±10%;(d) 单关生成改"重试 30 次取最优";(e) 结果对比文字显示百分比
- `workbench.html`:/暗钩列改显示密度百分比;汇总改"平均钩子密度"
- `functions/levels/[[path]].js`:后端返回新增 `hookDensity`/`darkHookDensity`

**稀缺度加权的实测效果**:

| 场景 | 原始钩子 | 有效钩子 | 分数 |
|---|---|---|---|
| 3 个独占型(每型只有 1 对,被埋了就没替代) | 3 | **3.0** | 84 |
| 3 个泛滥型(每型有 3 对,被埋了还有替代) | 6 | **2.0** | 61 |

## Day 22 · 8月18日（周二）：钩子定义扩展 + 分数公式封顶调整

### 一、钩子定义扩展（重大改动）

**用户反馈**："万一一块麻将 A1 和另一块麻将 A2 都在底层,但是 A2 被一堆待消除的麻将压着,这怎么算呢？要是想消除麻将 A1 的话,就必须先把压在 A2 上面的麻将都消除掉才能去拿。"

**原定义**（只算层差 ≥ 2 的对子）：
```js
if (t.layer - topLayer >= 2) buried++;
```

**问题**：同层被压、左右夹住的牌没被算作钩子，导致钩子数量偏少，调参数时分数波动很小。

**新定义**（任何形式的埋牌）：
```js
function isTileBuried(tile, allTiles) {
  // 1. 同层被压：有上层牌覆盖
  const hasUpper = allTiles.some(o => 
    o.id !== tile.id && o.layer > tile.layer && 
    Math.abs(o.row - tile.row) < 2 && Math.abs(o.col - tile.col) < 2
  );
  if (hasUpper) return true;
  // 2. 左右夹：同层左右都被夹住
  const sameLayer = allTiles.filter(t => t.layer === tile.layer && t.id !== tile.id);
  const hasLeft = sameLayer.some(t => t.col === tile.col - 2 && t.row === tile.row);
  const hasRight = sameLayer.some(t => t.col === tile.col + 2 && t.row === tile.row);
  return hasLeft && hasRight;
}
```

**埋牌三种形态**：
1. **层埋**（原定义）：同一对牌中，一张在顶层、一张深埋
2. **上压**（新加）：同层一张，被上层牌压住
3. **左右夹**（新加）：同层一张，左右都被夹住（边夹住）

### 二、分数公式封顶调整

**原公式**：`min(effHooks / 5, 1) × 30` — 5 个有效钩子就拿满分，再多没意义

**新公式**：`min(effHooks / 8, 1) × 30` — 8 个有效钩子才满分，让分数有更大波动空间

**效果**：
- 钩子数 5~8 之间能拉开分数差距（之前全是封顶 30）
- 暗钩封顶 5 → 8
- 可点率、层数维度不变

### 三、影响评估

| 项目 | 修改前 | 修改后 |
|---|---|---|
| 钩子定义 | 只看层差 ≥ 2 | 上压/左右夹都算 |
| 钩子封顶 | 5 | 8 |
| 暗钩封顶 | 5 | 8 |
| 钩子数 | 通常 0~5 | 通常 3~15 |
| 分数波动 | 小（个位数） | 大（10+） |

### 四、潜在风险

- 钩子数大幅增加，可能导致大多数关卡都接近封顶
- 需要实测一批关卡，确认分布合理
- 如有必要可再次调整封顶值

## Day 23 · 8月18日（周二）：加槽位压力维度 minSlots（解决"钩子拉满也不难"）+ 层级偏移回调

### 一、问题发现

用户反馈核心痛点：**"把钩子数量拉满，感觉也不会特别难"**。原版麻将有时会出现"消除顺序不对就死局"的情况——卡槽中已有的牌都被夹着或盖着，容错率暴跌。

用户举了一个具体例子：
> 一块麻将 A 可直接点击，另一块 A 被 B 盖住。如果你先点 B 进卡槽，而另一块 B 又深埋着，A 就会一直卡在槽里，容错率降低。原版困难关卡会有这种情况，但我们的游戏把钩子拉满也难出现。

**分析**：现有难度模型（钩子/可点率/层数）都是**静态指标**，只衡量开局一瞬间的状态。真正的难点是**动态的**——消除顺序导致的连锁困境（依赖链）。倒推法随机配对，依赖链普遍很短，所以"钩子拉满也不难"。

### 二、三个候选维度分析

要捕捉"动态难度"，需要新维度。分析了三个候选：

#### 候选 1：依赖深度（Dependency Depth）

**定义**：想消掉最深处的一对牌，需要先解开多少层前置依赖。

```
你点了 A1 进卡槽 → 想配对 A2，但 A2 被 B 压住
  → 想消 B，但 B2 被 C 压住
    → 想消 C，但 C2 又在更深的地方
      → 结果 A、B、C 都卡在槽里
```

- 依赖深度 1：A 被 B 压，B 可见 → 先消 B 就能消 A
- 依赖深度 3：A→B→C 链条 → 得消 C→B 才能碰 A

**问题**：和"层数"高度重复——层数已经在衡量"埋得深"。依赖深度只是层数的另一种表达。

#### 候选 2：陷阱牌比例（Trap Ratio）

**定义**：开局可点的牌里，有多少张是"点了就会让局面变难"的陷阱牌。

比如开局 10 张可点牌，其中 7 张点了之后会让最小槽位需求从 3 升到 5——玩家有 70% 概率第一手就踩坑。这解释了"看起来很简单的关卡，玩着玩着就死了"。

**问题**：计算量太大。每个可点选择都要跑一遍解算器看后续影响，生成速度会慢一个数量级。

#### 候选 3：最小槽位需求（minSlots）✅ 最终选择

**定义**：模拟一个聪明玩家的贪心打法，统计卡槽中最大同时存在的花色数（7 格上限）。

- minSlots = 2 → 容错极高，怎么玩都不容易死
- minSlots = 5 → 容错极低，走错一步槽就满了
- minSlots = 7 → 卡槽上限，几乎不可能完成

**为什么选它**：
1. 一次贪心模拟就能算，计算成本低
2. 直接对应玩家感知的"容错率"
3. 和现有维度（钩子/层数/可点率）不重复

### 三、贪心模拟算法（computeMinSlots）

```
board = 场上未点的牌（Set<id>）
slot  = 已进槽未配对的牌（Map<typeId, tile>）

while 还有牌或槽里有单张:
  1. 场上有可点的牌，其花色槽里已有 → 点它配掉槽里那张（槽位 -1）
  2. 场上有两张可点同花色 → 点掉（短暂过槽即消，不计峰值）
  3. 只能点单张 → 选"底下压牌最多"的进槽（尽早解锁被埋的牌），槽位 +1
  记录 slot.size 峰值
```

**策略设计的理由**：
- 优先级 1（配对槽内）：聪明玩家看到能配就会立即配，减少槽位占用
- 优先级 2（消现成对）：不消耗槽位
- 优先级 3（选压牌最多的）：尽早解锁被埋的牌，减少后续被迫存槽的情况

### 四、新难度公式

```
难度分 = (1-可点率)×40 + 层数×8
       + min(有效钩子/8, 1)×30
       + min(有效暗钩/8, 1)×20
       + min((minSlots-2)/4, 1)×30    ← 新增"槽位压力项"
       + 10
```

**槽位压力项解释**：

| minSlots | 分数 | 含义 |
|---|---|---|
| 2 | 0 | 容错极高 |
| 3 | 7.5 | 低压力 |
| 4 | 15 | 中等压力 |
| 5 | 22.5 | 高压力 |
| 6 | 30 | 极高压力（满分） |

### 五、生成控制：slotPressure 参数

倒推法加 `slotPressure`（0~1）参数控制配对策略。核心洞察：**倒推配对顺序 = 正向消除顺序的逆序**。

- **倒推前中期**（棋盘还满）按概率把一张最高层 + 一张最低层配对
- 正向玩时：高层那张早露、低层那张深埋 → 玩家被迫把早露那张存进槽里 → 槽位占用升高

```
slotPressure = 0   → 纯随机配对（不倒推叠层）
slotPressure = 0.5 → 默认（50% 概率叠层配对）
slotPressure = 1   → 最大化叠层配对
```

**实测数据**（T2 模板，各 15 次）：

| slotPressure | minSlots 范围 | 平均 | 分数平均 |
|---|---|---|---|
| 0 | 1~4 | 1.3 | 123.5 |
| 0.5 | 1~5 | 1.9 | 125.4 |
| 1 | 1~3 | 1.3 | 125.6 |

单个案例：minSlots=5 时分数 152（槽位压力项贡献约 22.5 分）。

minSlots ≥ 5 时显示 🔥 标识高槽位压力。

**目标分数问号弹层更新**：

- "各项含义"加槽位压力说明

### 九、心得

- **静态指标的天花板**：钩子/可点率/层数都是开局快照，无法捕捉"消除顺序不对就死局"的动态难度。minSlots 是第一个中盘指标。
- **贪心模拟足够好**：不需要完整 DFS 解算器。一个"优先配对、其次消现成对、最后选压牌最多的单张"的贪心策略，就能稳定反映槽位压力。
- **倒推法配对策略是关键**：纯随机倒推天然 minSlots 偏低（随机配对很少产生"同花色一张早露一张深埋"的结构）。slotPressure 在倒推时主动构造叠层配对，才能产出真正的"容错率低"关卡。

## Day 23 补充 · 8月18日（周二）：钩子加权改为"可见伴侣"加权

### 一、用户反馈的问题

用户看一关（74 张 / 37 对），数据说"钩子 95%"，但他**眼睛能看到 3 对可立即消除的牌**（1万、6万、龙）。直觉上"埋得不多"，但算法说有 35 对钩子。

### 二、根因分析

**原稀缺度加权**：每个钩子权重 = 1 / 该花色总对子数。

- 1 对 1 张埋 → 权重 1.0（独占型）
- 3 对 6 张埋 → 权重 0.33（泛滥型）

**问题**：如果某花色有 4 张（2 对），其中 3 张露在外面、1 张埋着：
- 算法：这是 1 对钩子，权重 1/2 = 0.5
- 玩家视角："埋的那张很容易找到，因为外面 3 张都长得一样"

### 三、新规则（用户提议）

**权重 = 1 / (同花色可见张数 + 1)**

| 场景 | 同色可见 | 权重 |
|---|---|---|
| 同色全部埋着，没人露 | 0 | 1.0 |
| 同色有 1 张露 | 1 | 0.5 |
| 同色有 2 张露 | 2 | 0.33 |
| 同色有 3+ 张露 | 3+ | ≤ 0.25 |

**直觉**：埋的牌同色**越容易看到**，就越**不容易忘**，权重越低。

### 四、代码改动

```js
// 新加权：每张埋牌的权重 = 1 / (同花色可见 + 1)
const buriedList = arr.filter(t => isTileBuried(t, tiles));
const hookInst = Math.min(buriedList.length, pairs);  // 按对数截断
for (let i = 0; i < hookInst; i++) {
  const t = buriedList[i];
  const sameVisible = arr.filter(o => o.id !== t.id && clickableSet.has(o.id)).length;
  effHooks += 1 / (sameVisible + 1);
}
```

| 3 | 93% | 65% | 114 |
| 4 | 93% | 62% | 122 |
| 5 | 96% | 63% | 123 |

用户截图场景（slotPressure=0，模拟"看起来简单"）：

加权后的钩% 和玩家"看得到的牌数"基本对得上了。

## Day 23 补充 · 8月18日（周二）：参数匹配改为反向驱动（方案 C）

### 一、问题

用户发现钩子滑块和分数范围存在逻辑矛盾：
1. **单关生成（按形状/按底座）**：只匹配钩子/暗牌参数，**完全不管分数**——设钩子 100% 但底座是口字形（几乎没钩子），系统只会静默重试到上限后返回"最接近的"

1. 用户设目标难度 110、容差 ±15

## Day 24 · 8月18日（周二）：Tab 双模式（参数模式 + 难度模式）+ 保存按钮 bug 修复

### 一、问题

钩子/暗牌/暗钩比例滑轮对另一名策划来说太抽象。
- 用户需要"我要多难的关卡"，不是"我要钩子 40% 的关卡"
- 钩子驱动分数但用户又单独设分数——两个来源矛盾

### 二、方案：Tab 双模式

**Tab 1：参数模式**（保留）
- 目标分数 min~max + 钩子/暗牌/暗钩三个滑轮
- 给老用户/精细调参用

**Tab 2：难度模式**（新增）
- 一个 1-10 滑轮
- 系统自动算出分数范围/钩子/暗牌比例
- 给新协作者/快速生成用

**难度映射**（实测分数范围 60~150）：

| 难度 | 分数范围 | 钩子 | 暗牌 |
|---|---|---|---|
| 1 | 50~70 | 10% | 5% |
| 5 | 82~106 | 41% | 12% |
| 10 | 122~151 | 80% | 20% |

**Tab 切换时同步滑轮值**：切到难度模式时，自动把对应的值写入参数模式的滑轮，避免两个 Tab 显示不一致。

**难度模式不严格匹配**：参数是自动分配的，不要求生成结果"命中"目标，直接接受第一个生成结果。

### 三、问题与修复

#### 1. 难度 10 的分数范围到不了 140~170

**原因**：文档说"实际多在 60~150"，170 是理论最大值。
**修复**：从 `60~170` 改为 `50~151`（d=1 ~ d=10）。

#### 2. 保存按钮没反应

**原因**：HTML 里的 id 是 `wbNewOrder`，但 JS 找的是 `wbSaveOrder`，对不上。`getElementById('wbSaveOrder')` 返回 `null`，`.value` 抛错，函数崩溃，**完全没反应**。
**修复**：
- 兼容两种 id（`wbNewOrder` 或 `wbSaveOrder`）
- 用 `try-catch` 包整个函数，再有异常弹 alert 而不是静默崩溃

#### 3. 错误提示是假的

**原因**：提示"试试调整参数或形状"，但用户不知道该调什么。
**修复**：
- 始终返回最接近的关卡（不再报错）
- 偏差说明客观化：只说"分数 X 高于上限 Y"，不再说"试试调什么"

| 文件 | 改动 |
|---|---|
| `editor/index.html` | 加 Tab 系统（参数/难度）、Tab 切换同步滑轮、难度模式自动映射、保存按钮 bug 修复 + try-catch |

### 五、心得

- **简化 ≠ 删功能**：Tab 模式让新人用难度滑轮、老用户用参数滑轮——同一个工具适配两类用户。
- **静默崩溃最可怕**：保存按钮"没反应"不是用户操作问题，是 JS 抛异常被吞了。今后所有关键 handler 都要 try-catch + 弹 alert。
