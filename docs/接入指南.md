# 麻将消一消 · 关卡 JSON 接入指南(给程序同学)

> 目标:让你拿到一份关卡 JSON 后,知道怎么把它喂进 demo,以及怎么自己生成/校验一份合法的关卡。
> 关联文档:[关卡JSON格式.md](./关卡JSON格式.md) 是字段速查表(本文更聚焦"接入路径"与"避坑")。

---

## 一、TL;DR

关卡 JSON = 一份**单关完整描述**。最小可玩版本只要 5 个字段(`levelId`、`totalPairs`、`tiles`、`specialTiles`、`rotation`),其他字段是工作台/编辑器扩展用的。

**两种接入 demo 的方式**:

| 方式 | 适用场景 | 接入点 |
|---|---|---|
| **iframe + postMessage** | 把 demo 嵌进自己的页面(编辑器/工作台/活动页) | 父窗口发 `{type:'loadLevel', level}` |
| **直接 import JSON 文件** | 离线试玩、调试关卡 | demo 顶部「导入关卡」按钮 |

---

## 二、最小可玩 JSON 示例

可以直接复制到 `demo/index.html` 里"导入关卡"试玩:

```json
{
  "levelId": 1,
  "totalPairs": 4,
  "tiles": [
    { "id": 1, "layer": 0, "row":  0, "col": -2, "typeId": 1, "isDark": false },
    { "id": 2, "layer": 0, "row":  0, "col":  2, "typeId": 1, "isDark": false },
    { "id": 3, "layer": 0, "row": -2, "col":  0, "typeId": 2, "isDark": false },
    { "id": 4, "layer": 0, "row":  2, "col":  0, "typeId": 2, "isDark": false }
  ],
  "specialTiles": [],
  "rotation": null
}
```

**必填校验**(demo 导入时会卡):

1. `tiles` 必须存在且为数组,长度 ≥ 2
2. 每张 `tile.typeId` 不能为 `null`(吐牌机本体除外,见下)
3. `tiles.length` 必须为**偶数**(成对消除)

**强烈建议**但 demo 不强制校验的:
- `tiles.length % 2 === 0` 且每个 `typeId` 出现**偶数次**(否则死局)
- `id` 唯一,1 起递增(用作 DOM key,重复会渲染错乱)

## 三、字段定义

### 3.1 顶层

| 字段 | 类型 | 必填? | demo 是否消费 | 说明 |
|---|---|---|---|---|
| `levelId` | int | 否 | ✓(显示用) | 关卡序号,任意整数,仅做标题展示 |
| `totalPairs` | int | 否 | △ | = `tiles.length / 2`,不传 demo 会自己算 |
| `tiles` | array | **✓** | ✓ | 牌列表(见 3.2) |
| `specialTiles` | array | 否 | ✓ | 暗牌/吐牌机的**重复声明**(见 3.3) |
| `rotation` | object\|null | 否 | ✓ | 旋转配置(见 3.4) |
| `_difficulty` | object | 否 | ✗ | 难度指标,只读参考 |
| `order` / `status` / `playTimeMs` / `key` / `name` / `createdAt` | * | 否 | ✗ | 工作台元数据,demo 不读 |

### 3.2 `tiles[]` —— 每张牌

```json
{ "id": 1, "layer": 0, "row": -2, "col": 2, "typeId": 1, "isDark": false }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✓ | 1 起递增唯一编号,demo 用作 DOM 标识,重复会渲染错乱 |
| `layer` | ✓ | 层号,**0 = 底层**(最先可点);层数越大越靠上 |
| `row` | ✓ | 上下(纵)坐标,**std 坐标**,见 3.5 |
| `col` | ✓ | 左右(横)坐标,**std 坐标**,见 3.5 |
| `typeId` | ✓ int\|null | 花色编号;**两张同 typeId 配对消除**;吐牌机本体传 `null` |
| `isDark` | ✓ bool | 暗牌(看不到正面,点击先翻面再消) |
| `type` | 可选 `"spitter"` | **吐牌机本体**标记(不可参与配对) |
| `dir` | 可选 `up`/`down`/`left`/`right` | 吐牌机吐牌方向 |
| `count` | 可选 int(1~8) | 吐牌机队列数量(初始不可见的备用牌) |
| `spitterOrder` | 可选 int(1 起) | **队列牌**序号,1 = 最先显示;非本体,`typeId` 正常 |

> **队列牌 vs 本体**:本体有 `type: 'spitter'`,`typeId: null`,不参与配对;队列牌是普通牌(可配对)只是按顺序"藏在"吐牌机里,带 `spitterOrder` 标记。

### 3.3 `specialTiles[]` —— 冗余声明(可选)

与 `tiles` 里的 `isDark`/`type: 'spitter'` 是**同一件事的两笔记录**:

```json
{ "id": 5, "type": "dark",     "layer": 1, "row": -3, "col": -5 }
{ "type": "spitter", "layer": 0, "row":  2, "col":  0, "direction": "up", "count": 3 }
```

demo 读端**只用一个来源**(优先 `tiles`)。写端可以**只写 `tiles` 不写 `specialTiles`**,demo 一样能跑。**写两边时必须保证 `id` 对齐**,否则 demo 会对同一张牌重复翻面/重复算吐牌。

#### 3.3.1 吐牌机(spitter)机制实现细节

吐牌机不是"运行时生成新牌",而是**预生成 + 渐进揭示**:

| 概念 | 实现 |
|---|---|
| 本体(spitter) | `type: 'spitter'`, `typeId: null`,带 `dir` + `count`,一直显示到队列用尽 |
| 队列牌 | 普通 tile,带 `spitterOrder: 1..count`,**全部预生成**在 `tiles[]` 里 |
| 队列牌位置 | 全部位于 spitter 的 **target 位置**(同 layer,沿 dir 方向偏移 2 格) |
| target 位置计算 | `up`: row-2;`down`: row+2;`left`: col-2;`right`: col+2 |
| 当前可点队列 | 只有 `spitterOrder === released + 1` 那张(其它被 z-index 高的 spitter 视觉遮挡) |
| 揭示触发 | 点当前可点的队列牌 → `spitterReleasedCount[spitterId]++` → 下一张获得 reveal 动画 |
| 揭示结束 | 当 `spitterOrder === count` 被点时,spitter 本体进入 `spitterExhaustedIds`,停止渲染 |
| 进度记录 | `spitterReleasedCount: Map<spitterId, count>`(初始 0) |
| target 位的普通牌 | 即使被队列牌压住,demo 也**强制可点**(让玩家先消除覆盖牌让队列牌露出来) |
| 点 spitter 本体 | **只触发提示,不消耗次数**(spitter 本体无实际消除逻辑) |

**重要不变量**:

- **所有队列牌生成时就存在**(`tiles.length` 已经包含它们),只是被 spitter 视觉遮住
- **生成器自动生成**:编辑器画完 spitter 后,生成器按 `sp.count` 在 target 位置生成对应数量的队列牌(都在同一 layer),填色时与普通牌一起参与配对校验
- **总牌数必须偶数**:`普通牌数 + count` 必为偶数,否则死局
- **spitter 本体的可点判定**与普通牌不同:**只检查不被上层覆盖**,不检查左右夹住(因为是装饰物)
- **spitter 本体不参与旋转**(`demo/index.html:982` 硬编码 `if (t.type === 'spitter') return false`)

**JSON 完整示例**(一个 spitter + 3 张队列牌 + target 位普通牌):

```json
{
  "levelId": 1,
  "totalPairs": 4,
  "tiles": [
    { "id": 1, "layer": 0, "row":  0, "col": -2, "typeId": 1, "isDark": false },
    { "id": 2, "layer": 0, "row":  0, "col":  2, "typeId": 1, "isDark": false },
    { "id": 3, "layer": 0, "row": -4, "col":  0, "typeId": 2, "isDark": false, "spitterOrder": 1 },
    { "id": 4, "layer": 0, "row": -4, "col":  0, "typeId": 3, "isDark": false, "spitterOrder": 2 },
    { "id": 5, "layer": 0, "row": -4, "col":  0, "typeId": 2, "isDark": false, "spitterOrder": 3 },
    { "id": 6, "layer": 0, "row":  4, "col":  0, "typeId": 3, "isDark": false },
    { "type": "spitter", "layer": 0, "row": -2, "col":  0, "dir": "up", "count": 3 }
  ],
  "specialTiles": [],
  "rotation": null
}
```

注意:
- id 1~6 都是普通牌(可配对、可消除)
- spitter 本体**没有 id**(编辑器惯例)
- id 3/4/5 是三张队列牌,都在 spitter 的 target 位置(`row: -4 = -2 - 2`),共享同一个坐标
- id 1+2 配对、id 3+5 配对(同 typeId 2),id 4+6 配对(同 typeId 3)→ 4 对

**队列牌消费流程**:

1. 初始:`spitterReleasedCount[id] = 0`,只显示 `spitterOrder=1` 的牌(id=3),其它两张被 spitter 视觉遮住
2. 玩家点 id=3 → `releasedCount=1` → 揭示 id=4(reveal 动画从下方弹入,因为 spitter 在 target 下方,dir=up)
3. 玩家点 id=4 → `releasedCount=2` → 揭示 id=5
4. 玩家点 id=5(spitterOrder===count)→ spitter 本体进入 exhaustedIds → 本体从 DOM 移除

### 3.4 `rotation` —— 旋转配置

```json
"rotation": {
  "centerRow": 0,
  "centerCol": 0,
  "radius": 2,
  "direction": "clockwise"
}
```

| 字段 | 说明 |
|---|---|
| `centerRow` / `centerCol` | 旋转中心 std 坐标 |
| `radius` | 半径(Chebyshev 距离,单位是 std 格)。`0` 或 `null` = 不旋转 |
| `direction` | `"clockwise"`(顺时针 ↻)或 `"counterclockwise"`(逆时针 ↺) |

**效果**:玩家每次点牌进卡槽,**被点那张直接飞入槽**,外圈按指定方向旋一格。详见 [3.4.1 旋转机制实现细节](#341-旋转机制实现细节)。

#### 3.4.1 旋转机制实现细节

旋转触发 + 执行的完整流程:

| 阶段 | 做什么 |
|---|---|
| **触发判定** | 点牌时,demo 检查是否存在满足旋转条件的牌(`tile.id` 之外、`t.layer === 0`、非 spitter、Chebyshev 距离 `0 < d ≤ radius`) |
| **被点牌** | **直接飞入卡槽**(不等动画,占据 `slots[emptyIdx]`) |
| **数据更新** | 调 `rotateTiles()` 修改其他牌的 `row`/`col`(见下) |
| **DOM 更新** | `render()` 重画所有牌的真实新位置 |
| **动画搬运** | 对每个被旋转的牌,clone 旧 DOM 元素,从旧 `getBoundingClientRect()` 动画(0.4s ease)到新位置 |
| **reveal 动画** | 同时 `spitterRevealedIds` 被清空,触发下一张队列牌的 reveal 弹出 |

**`rotateTiles` 算法**(核心):

```
对所有 t.layer === 0 且 Chebyshev 距离 d ∈ (0, radius] 的牌:
  1. 计算边界 minR/maxR/minC/maxC(由参与旋转的牌决定)
  2. 顺时针:顶行 col+=2 → 右列 row+=2 → 底行 col-=2 → 左列 row-=2
     逆时针:反方向
  3. 每边步进 = 2 格(TILE=2,一整块麻将宽度)
  4. 角点(同时是顶+右等)有冗余分支,效果一致
```

**重要不变量**:

- **中心点本身不会旋转**(`chebyshev > 0` 排除,中心位置即使有牌也保持不动)
- **只旋转 L0**(`t.layer > 0` 直接 return false);多层堆叠的上层**不动**
- **不旋转 spitter 本体**(`t.type === 'spitter'` 直接 return false)
- **不旋转被点的那张牌**(只搬运其他牌;被点那张直接飞入卡槽)
- **step = 2**(因为一块麻将占 2 格,半径和步进都是 2 的倍数才有意义;`radius=1` 就是紧贴中心的外圈 8 张)
- **`rotationConfig` 全局读**:`loadLevel` 时 `rotationConfig = json.rotation || null`;重玩/重新 import 会重置 `rotationState = 0`

**视觉反馈**(编辑器侧,接入 demo 不需要关心):

- 旋转画笔激活时,canvas 画两层虚线方框(外框=center±radius,内框再缩 1 块麻将) + 中心十字准星 + 实心圆点
- 顺时针红色 `#e85d6d`、逆时针蓝色 `#5b8fe8`
- **永远显示完整区域,不依赖麻将存不存在**(空棋盘上也能看清转的圈)

**与可点判定的交互**:

- 旋转是**位置变换**,不影响 `typeId`(配对关系不变)
- 旋转后,demo 重新调 `render()`,重新计算每张牌的"可点"状态(可能会让之前被夹住的牌变可点,或反之)
- 旋转可能让 spitter target 位的牌露出来,触发队列牌揭示

**示例**:半径 1、顺时针下,8 张外圈牌的搬运:

```
  [-2, -2]→[ 0, -2]→[ 2, -2]→[ 2,  0]→[ 2,  2]→[ 0,  2]→[-2,  2]→[-2,  0]→[-2, -2]
```

每次点牌,这 8 张的坐标沿外圈各自向前推一格(±2)。

### 3.5 坐标约定(std)

**最容易出错的部分**——三个要点:

1. **`row` = 上下(纵),`col` = 左右(横)**。**不是 x/y**。被当 x/y 处理会整体镜像。
2. **相邻牌相差 2**:一块麻将占 2×2 格子。同层横向紧挨的两张 `col` 差 2;纵向 `row` 差 2。
3. **层叠**:`layer` 越大越靠上;上层牌**每层左偏、上偏 1 单位**(半格),造成 3D 错层观感。

### 3.6 可点判定详解

游戏规则的核心,程序同学实现 demo 必须正确处理:

**普通牌可点**(全部满足):

1. **正上方无覆盖牌**:上层 `t.layer > this.layer` 的牌,若 `|row差| < 2 且 |col差| < 2`,则覆盖
2. **同一层左右不同时被夹**:同 `layer` 同 `row` 且 `col` 差恰好 2 的牌,**同时**左、右各有一张 → 不可点(只差一边可点)

**spitter 本体可点**(特殊,只满足 1):

- 只检查上层覆盖(`other.layer > spitter.layer && overlaps(other, tile)`)
- **不看左右夹住**(装饰物,允许任意位置被点)

**target 位的普通牌可点**(强制可点):

- 即便被队列牌压住,demo 也**强制判为可点**
- 让玩家能先消除覆盖在 spitter target 上的普通牌,把队列牌"挖"出来

**队列牌可点**(默认隐藏):

- 只有 `spitterOrder === released + 1` 的那张被计入 `active`(其它被 z-index 高的 spitter 视觉遮住)
- 队列牌本身的可点判定**仍然适用**:它必须在同 layer 不被夹、不被上层覆盖

**暗牌可点**:

- 同普通牌的可点规则(暗牌不影响可点性,只影响视觉:看不到正面)
- 选中时显示金色光晕

### 3.7 暗牌(`isDark: true`)行为

点击交互(PROG-0224 暗牌选取规则):

| 当前状态 | 点暗牌 A 后 |
|---|---|
| 无选中 | 翻面 + 选中(A 保持正面,显示金色光晕) |
| 已选明牌 B | 翻面 + 进卡槽 + `checkMatch(B, A)`(异色则 B 出槽回棋盘) |
| 已选暗牌 A | 翻面 + 进卡槽 + `checkMatch(A, A2)`(异色则 A 出槽回棋盘) |
| 已选暗牌 A,点暗牌 B(异色) | A 翻回背面;B 翻面 + 选中转移 |

**暗牌在卡槽里**:

- 暗牌**不显示正面**直到被配对消除
- 配对成功时:`checkMatch` 触发,两张一起消除,卡槽里其它牌**不挪动**(demo 行为:每张牌独立占一槽)
- 暗牌进槽后,牌面图片消失,只显示一个深色背盖

**翻面动画**:

- `justFlipped: Set<id>` 在 `loadLevel` / `flipAndShowFace()` / `render()` 之间追踪刚翻面的牌
- `render()` 时给这些牌加 `tile.flip` class,触发 0.3s Y 轴翻转动画

**暗牌与 spitter 队列牌**:

- 队列牌可以是暗牌(`spitterOrder: 1, isDark: true`)
- 但揭示时仍是同 spitter 的逻辑:被点 → released++ → 下一张揭示
- 玩家看到的是"翻面 → 配对 → 消除"的完整流程

### 3.8 卡槽机制

**槽位**:

- demo 有 **4 个固定槽位**(`slots = [null, null, null, null]`)
- 玩家点的牌按到达顺序填入,**最早入槽的占 `slots[0]`**
- 一旦 4 个槽都满,**仍然可以继续点击**新牌——但每张新牌入槽前会先触发 `checkMatch`:
  - 若新牌与槽内任一牌同 typeId → 配对消除,槽位释放
  - 若无配对 → 槽满时**新牌被自动入最旧的槽**(顶替最旧的牌)?——不,实际是:**继续旋转外圈但不入槽**,直到槽内有空间

**入槽流程**(`handleTileClick` → `flyInToSlot`):

1. **先查空槽**:`slots.indexOf(null)`,若返回 -1(全满)→ **直接游戏失败**(`showMessage('💀 卡槽满了')`)
2. 标记 `slotTileIds.add(tile.id)`(防止重复入槽)
3. `slots[emptyIdx] = tile`(立即占位,避免点击过快时两张瞄准同一个空槽)
4. 渲染卡槽 DOM
5. 触发动画:旧屏幕位置 → 卡槽位置的飞行轨迹(0.4s ease)

**配对触发**:

- 每次入槽后立即调 `checkMatch`:
  - 扫所有 `slots[i].typeId`,找两张同 typeId 的槽位
  - 找到 → 两张飞入 + 消除 + 槽位置 null(其它槽**不动**)
  - 找不到 → 等下一次入槽
- 配对后**二次校验**:`slots.every(s => s !== null)` → 显示「💀 卡槽全满」游戏结束

**暗牌 + 明牌配对**:

- demo 允许暗牌与同 typeId 明牌配对
- 暗牌先飞入槽,动画完成后再让明牌飞入,触发 `checkMatch`
- 暗牌翻面 + 配对消除的动画序列见 `demo/index.html:746`

**卡槽容量上限**:

- **4 槽硬编码**(`slots = [null, null, null, null]`)
- 策划难度维度 `minSlots`(最优打法下最大占用)以此为基准
- **卡槽满 = 游戏失败**(无自动失败检测,需玩家手动失误触发)

### 3.9 配对与消除机制

**`checkMatch(slots)` 触发时机**:

- 每次有牌入槽(`handleTileClick` 末尾)
- 队列牌被点击后(暗牌版翻面 + 配对)

**匹配逻辑**:

```
扫描 slots:
  for each i in [0..3]:
    if slots[i] === null: continue
    for each j in [i+1..3]:
      if slots[j] !== null && slots[i].typeId === slots[j].typeId:
        配对消除 slots[i] 和 slots[j]
        slots[i] = slots[j] = null
        break
```

**消除动画**:

- 两张牌同时飞向中央消失(0.3s ease)
- 动画完成后从 `slotTileIds` 移除
- 槽位置 null,卡槽 DOM 更新

**与旋转的交互**(旋转触发分支):

- 见 [3.4.1](#341-旋转机制实现细节):旋转动画是**被点牌外的所有牌搬运**
- 如果旋转动画进行中又触发了一次配对,**两者并行**(动画层独立)

### 3.10 通关判定

**`checkWin()` 触发**:

- `loadLevel` 之后每次牌状态变更(消除 / 旋转 / 暗牌翻面)
- 判定:`active.length === 0 && slots.every(s => s === null)`
- 即棋盘无活动牌 + 卡槽无牌 = 通关

**通关后**:

- `gameOver = true`
- 通过 `postMessage` 发 `{type: 'playFinished', durationMs}` 给父窗口
- 持久化最佳成绩到 `localStorage['mahjong_best_' + levelKey()]`
- `levelKey()` 是关卡指纹:`tiles.length + ':' + darkCount + ':' + 前 3 张牌的 layer,row,col`(轻量 hash,不依赖 `key` 字段)
- 显示通关弹窗:本局用时 + 历史最佳 + 「再来一次」按钮

**死局判定**:

- demo **不主动检测死局**(无自动失败)
- 玩家点无可点的牌时,demo 显示「提示」(`showHint`),不报错
- 卡槽满 + 无可消配对 = **游戏失败**,显示「💀 卡槽全满」

### 3.11 `_difficulty` 字段(只读参考)

生成器在写出关卡时**自动计算**,程序同学读 JSON 时会遇到。**不影响 demo 运行**,仅作难度指标展示:

| 字段 | 含义 |
|---|---|
| `score` | 总难度分,公式 `clickRatio × 30 + maxLayer × 8 + 钩子埋深加权 + 暗钩 + 槽位压力 + 队列压力 + 5` |
| `clickRatio` | 开局可点牌占比(越低越难) |
| `hooks` / `effHooks` | 钩子对子数 / 埋深加权钩子 |
| `darkHooks` / `effDarkHooks` | 暗钩数 / 有效暗钩 |
| `hookDensity` | `hooks / totalPairs`(≤ 1) |
| `maxLayer` | 最高层(0 起) |
| `minSlots` | 最优打法下卡槽最大占用(越高容错越低,7 封顶) |
| `slotSolvable` | 贪心求解算法是否判定可解 |
| `typeCount` | 花色种数 |
| `queueCount` / `hiddenQueueCount` | 吐牌机队列数 / 隐藏压力队列数 |
| `totalPairs` | 总对数 |
| `spitterQueuePressure` | 队列压力分(详细公式见 [generator.js:635](麻将消一消_在线/editor/generator.js:635)) |

### 3.12 渲染与 z-index 体系

程序同学实现 demo 渲染时,层级关系要正确:

| 元素 | z-index 公式 |
|---|---|
| 普通牌(L0) | `t.layer * 1000 + t.id` |
| 上层牌(L1+) | `t.layer * 1000 + t.id`(越大越靠上) |
| spitter 本体 | `10000 + t.id`(永远在最上) |
| 队列牌 | `10000 + t.id`(与 spitter 同层,但 spitter 后渲染会盖住) |
| 卡槽元素 | 由 DOM 顺序决定(在棋盘之后渲染) |
| 飞行动画的 clone 元素 | `9999`(临时,动画结束移除) |

**层叠偏移**(`layerOffset`):

- 上层牌**每层左偏、上偏 1 单位**(半格),造成 3D 错层观感
- spitter 本体和队列牌**不应用偏移**(保持在自身位置,避免与吐牌机标识重叠)

**`baseBounds`**:

- `loadLevel` 时调 `computeBounds(tiles)` 固定一次
- 旋转、消除都不重算(镜头缩放不变化,避免抖动)

## 四、`typeId` 与花色

demo 侧的 `typeId` 含义:

| typeId 范围 | 含义 |
|---|---|
| 1 ~ 9 | 一万 ~ 九万 |
| 10 ~ 18 | 一条 ~ 九条 |
| 19 ~ 27 | 一筒 ~ 九筒 |
| 28 ~ 34 | 东南西北中发白(循环补) |

- **配对 = 两张同 `typeId`**(与麻将字面无关,只看编号)
- **必须成对**:每个 typeId 出现偶数次
- **typeId 从 1 起**,`0` 或 `null` 表示"未填色"或"吐牌机本体"

> ⚠️ `typeId` 是**逻辑编号**,不是牌面图。demo 启动时会随机把 45 张真实麻将图分配给当前会话的 typeId,所以同一 typeId 在不同会话里看到的牌面可能不同。**别把 typeId 当成"花色名"理解**。

## 六、生成一份合法 JSON 的步骤

**手写最小关卡**:

1. 画一个 4 张牌的 2×2 阵列(实际坐标 `row` 和 `col` 相差 2)
2. 给两张同 typeId,另两张同另一 typeId
3. 写 4 个 `tile`,`id` 1~4
4. `specialTiles: []`,`rotation: null`
5. 保存为 `.json`,demo 导入即可

**程序生成关卡**:

1. 调用 `麻将消一消_在线/editor/generator.js` 的 `generateLevel(options)` 或 `fillEditorShape(editorTiles, editorSpecial, options)`
2. `options.rotation = {centerRow, centerCol, radius, direction}` 可选
3. 返回的对象**直接就是合法 JSON**(顶层含 `tiles`、`specialTiles`、`rotation`、`_difficulty`)

生成器的关键校验(写入前会 throw):
- 牌数必须偶数
- spitter `count` 必须在 1~8
- 普通牌 + 队列牌总数必须偶数
- L1+ 吐牌机的 target 位置必须有支撑(下方有下层牌)

## 七、避坑清单

按出错频率排:

1. **坐标反了**:`row` 是上下不是左右。被当 x/y 处理,棋盘整体镜像。
2. **typeId 不成对**:奇数次 → 死局。校验 `tiles.length` 偶数 + 每个 typeId 偶数次。
3. **`isDark` 和 `specialTiles` 重复且 id 不对齐**:demo 会重复翻面。建议**只写一边**(优先 `tiles.isDark`)。
4. **id 重复或非递增**:demo 用 id 做 DOM key,重复 → 渲染错乱或丢牌。
5. **吐牌机本体写了 typeId**:本体必须 `typeId: null`,否则 demo 会试图拿它配对。
6. **rotation 在多层塔上**:目前只旋转 L0;上层牌(`layer > 0`)不会被旋转,如果想让它们也转,需要改 demo。
7. **rotation 中心放在没有牌的位置**:不影响功能(动画照常搬运外圈),只是视觉上"转的圈"看着空。
8. **typeId > 34**:会循环回到东南西北中发白,可能不符合预期花色;确保 `typeCount` 在 34 以内。
