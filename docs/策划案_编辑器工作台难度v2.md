## 一、系统总览：3 段式架构

```
浏览器（编辑器 / 工作台 / 游戏）
  │ HTTP
  ▼
Cloudflare Pages（服务器）
  │ 静态托管 + Pages Function（API）
  │ git push -> 自动部署
  ▼
GitHub 仓库（数据库）
  ├── editor/  workbench.html  docs/  ...
  ├── functions/levels/[[path]].js   ← 后端 API
  ├── version.json                   ← 版本检测
  └── data/levels/*.json            ← 关卡（每关一个文件）
```

**关键点**：关卡数据**不存在任何云服务的硬盘上**——全部在 GitHub 仓库的 `data/levels/` 目录里，每关一个 JSON 文件。换服务器只换"中转"，数据天然跟着仓库走。

## 二、编辑器 v4.0：浅色重构（Day 17–18）

### 解决了什么

- 原 v3.1 是通用深色游戏后台风，视觉疲劳、操作习惯不符合策划工作（弹窗 alert、缺撤销/缩放/拉伸）
- 关卡/工作台两个页面风格完全割裂（一个深色一个浅色）

### 设计选择

| 选择 | 理由 |
|---|---|
| 浅色卡片风（米白底 + 白卡片 + 赭金强调） | 策划长时间工作不刺眼，参照成熟笔记/表格类工具 |
| 红色只留给危险操作 | 解决原版"激活层=红、删除确认=红"的语义混淆 |
| 顶栏（文件/撤销/视图/帮助）+ 左侧栏卡片（图层/画笔/生成）+ 画布 + 右侧预览 | 把"创作"侧栏和"管理"侧栏分开，工作台不挤进来 |
| 3 栏之间可左右拖拽 + 宽度记忆 | 适应不同用户的窗口习惯和内容长度 |
| 滚轮 = 缩放，空格/中键 = 平移 | 符合主流编辑器（Figma/地图）习惯，避免"上下滑扫过空白" |
| 自动保存到 localStorage | 防止误关页面丢工作 |
| 撤销/重做（Ctrl+Z/Y）、右键擦除、Delete 删单张 | 编辑器刚需，之前都没有 |
| 牌面不加 L 层标签，上层牌左偏 3px 露出下层边 | 标签挡图案；左偏让堆叠高度一眼可读 |
| 工作台从顶栏**新窗口打开**（window.open） | 编辑器不丢上下文 |

### 重点 UI 决策（基于策划反馈迭代）

- **画布收窄到牌区**：原 14 列只用了 12（牌占 -5..5），两边空白
- **默认视图填满**而非留白：避免"滚轮上下滑看到大片空白"
- **"关卡名 + 第几关"双字段**：关卡名是身份（unique），第几关是排序位
- **状态（制作中/待测试/已完成）整块砍掉**：会变成要维护的元数据，但不产生直接价值
- **保存挪到预览面板**：生成->试玩->保存，连贯动作在同一处完成
- **保存栏两行布局**：第一行 口令+关卡名，第二行 第几关（带标签）+保存+收起；原来一行 5 个控件太挤

## 三、工作台独立成页（`workbench.html`）

### 为什么独立成页，不放侧栏

- 关卡量级：**几百~上千关**（前期目标）
- 侧栏 264px 宽装不下密集表格
- 独立页能用全屏宽度，渲染快、易搜索

### 功能清单

| 功能 | 实现 |
|---|---|
| 口令连接 | sessionStorage 存口令（编辑器和工作台页共享） |
| 汇总计数 | 共 N 关 / 已排号 M / 未排号 K / 总张数 / 平均难度 |
| 搜索 | 关卡名模糊搜索 |
| 排序 | 序号 / 难度分 / 张数 / 保存时间 / 名称 |
| 筛选 | 全部 / 已排号 / 未排号 |
| 行内改序号 | 输入框 -> 失焦 PATCH |
| 行内改名 | 输入框 -> 失焦 PATCH |
| 下载/删除 | 按钮 -> 触发 API |
| **试玩时长列** | `formatPlay(lv.playTimeMs)`，显示最佳成绩 |

### 不做（明确砍掉）

- ❌ 状态徽章（进度追踪交给 GitHub 提交记录 / 备注，不进工具）
- ❌ 作者列（不在工具里暴露另一策划的名字）
- ❌ "加载到预览"按钮（编辑器是创作场景，工作台是管理场景，混在一起会乱）

## 四、难度公式 v2（Day 18，核心改动）

### v1 -> v2 改了什么

**问题**：v1 钩子项用 `min(钩子数÷总牌数×100, 1) × 30`——百来张牌时只要 1 个钩子占比就超过 1、拿满 30 分。**钩子项退化成"有/无"开关**，1 个和 5 个钩子同分。

**改法**：`min(钩子数/5, 1) × 30`——每 1 个钩子 +6 分，5 个拿满 30。暗钩子同理。

| 项 | v1 | v2 | 满分 |
|---|---|---|---|
| 可点率 | `(1-可点率)×40` | 同 | 40 |
| 层数 | `层序×8` | 同 | 40 |
| 钩子 | `min(占比,1)×30` | **`min(钩子数/5,1)×30`** | 30 |
| 暗钩子 | `min(占比,1)×20` | **`min(暗钩数/5,1)×20`** | 20 |
| 保底 | +10 | 同 | 10 |

**分母 5 怎么定的**：实测 80~110 张牌的标准关卡，钩子数观测 0~5（中位 2），5 个封顶正好覆盖。

### 实测效果

同底座 12 关（同底座，只花色/堆塔不同）：
- v1：121~127 全挤在 7 分范围
- v2：65~130 拉开 65 分，**每钩 ~10 分阶梯**（暗牌版+10，亮牌版+6）

### 已知局限（诚实记录）

- **可点率只拍开局一瞬间**——中盘难度不计入（但倒推法保证可解，不会真卡死）
- **花色种类数已统计但没进公式**——如果以后需要，可加"一对一花色占比"小项
- **跨模板、跨版本不可比**——绝对分只能在同系列内排序

### 校准闭环

这是 v2 最重要的副产品：**试玩计时**让公式第一次可证伪。用分数 vs 通关时间的相关性来校准权重。

## 五、试玩计时闭环（Day 18，经三轮打磨）

```
生成关卡 -> demo 加载 -> 「⏱ 计时并开始游戏」按钮（遮罩盖住 demo）
    ↓ 点击按钮
计时开始（编辑器 ⏱ mm:ss 滚动）
    ↓ 玩家试玩…
通关 -> demo 显示「本局 X · 最佳 Y」+「🔄 再玩一次」按钮
    ↓ postMessage playFinished 给编辑器
编辑器记录试玩历史（最近 5 次），最佳成绩 = Math.min(所有记录)
    ↓ 点保存到工作台
playTimeMs = 最佳成绩（不是最后一次）
    ↓
工作台"试玩"列显示最佳成绩
```

**三轮打磨的教训（为什么是按钮+最佳成绩）：**

| 版本 | 触发方式 | 问题 |
|---|---|---|
| v1 | 关卡加载即计时 | 包含"看牌不算玩"的时间 |
| v2 | 首次点击牌 | 玩家觉得"点一下就开始了？我没准备好" |
| v3（现在） | **「计时并开始游戏」按钮** | 玩家准备好才开始；通关后可**再玩一次**，保存时自动取**最佳成绩** |

**demo 侧**：最佳成绩存 localStorage（按关卡指纹分键），通关界面显示本局/最佳/再玩一次。**编辑器侧**：维护 `levelPlayHistory`，保存时用 `Math.min`。

## 五点五、版本更新自动提示（Day 18 补充）

双人协作的核心问题：**改完代码，另一位策划不知道要刷新**。方案：

- 仓库根放 `version.json`（含当前部署的 commit hash）
- 编辑器内嵌 `window.APP_VERSION`
- 每 5 分钟 fetch 比对 → 不一致弹顶部横幅「请强刷 Ctrl+Shift+R」
- **部署纪律：每次推代码必须同步更新两处 hash**

数据同步不受版本影响（新旧前端读写同一 GitHub 后端）。

## 五点六、堆塔对称性修复（Day 18 补充）

**现象**：对称底座按底座生成，约 20-30% 概率报「堆层校验失败」。

**根因**：奇数张时"删顶层任意一张凑偶"破坏了镜像对称（删了 A 但留着 A 的镜像 B）。

**修法**：奇数时成对删除（一张+它的镜像）；顶层找不到镜像对则删中轴线上的牌（row=0，自身对称）。修复后 100 次生成 0 失败。

**坐标系说明**（排查时理清的）：编辑器 std 坐标（row=纵/col=横）进生成器后交换为内部坐标（row=横/col=纵）。底座对称检测用 std col-mirror，校验用 internal row-mirror，二者经坐标交换后**等价**。堆塔展开用 internal row-mirror，三者一致。

## 八、设计原则（沉淀）

1. **不解决"已解决"的问题**——基础功能（生成/导出/试玩）做对就够，不堆叠
2. **删除 > 添加**——砍掉的永远比加上的多：状态、作者、"加载到预览"……每个砍掉都让界面更清晰
3. **数据可证伪 > 拍脑袋调参**——试玩计时让难度公式第一次有反馈环路
4. **最佳成绩 > 最后一次**——策划要测的是关卡难度，不是手抖；多次试玩取 min
5. **架构可移植**——后端只调 GitHub REST API，10 行代码可换任何 serverless 平台
6. **同一份逻辑多端口**——git 仓库是单一真相源，编辑器/批量工具/工作台都从同一份代码渲染
7. **少部署**——攒批推代码，既省额度又让版本检测更准确

## 九、Day 20 新增(2026-08-18)

### 9.1 Demo 动画系统

**飞入卡槽动画**(`flyInToSlot`):
- 克隆牌从棋盘当前位置飞向卡槽,`@keyframes flyIn` 位移+缩小+淡出
- 点击后**立即**从棋盘移除(不再阻挡下方牌),动画只作视觉反馈

**匹配消除动画**:
- `@keyframes matchedOut`:配对牌缩放弹跳后消失(0.3s)
- `checkMatch` 先加 `matching` 类,动画结束后再清除

**暗牌匹配流程**:
- 先翻开( flipIn 动画 320ms) → 再飞入卡槽(不再直接消失)

### 9.2 生成器冲突检查修正

**原问题**:间距为 1 的相邻牌被误判为"重叠",田字格/实心底座 100% 失败

**修法**:只禁止完全重合(`row===row && col===col`),允许相邻

**效果**:
| 底座 | 修复前 | 修复后 |
|---|---|---|
| 田字格 2×2 | 0/10 | 10/10 |
| 实心 4×5 | 0/5 | 5/5 |

### 9.3 生成参数重构

**删除冗余**:暗钩目标 = 钩子目标 × 暗钩比例,三者独立会矛盾

| 改动 | 说明 |
|---|---|
| 删"暗钩目标"滑块 | 消除冗余 |
| "暗钩覆盖率"→"暗钩比例" | 更直观 |
| 新增"≈ 暗钩目标"只读显示 | = 钩子目标 × 暗钩比例 |

### 9.4 批量生成候选池

**问题**:暗钩目标默认 20%,实际多数 0~5%,批量出 0 关

**修法**:分数范围内未结构命中的关卡存入候选池,最终按偏差排序取最接近的,状态栏提示"部分取最接近目标的"

### 9.5 堆塔死形重搭

**问题**:旧代码用同一死形重试 100 次白白浪费

**修法**:外层 30 次重搭新塔形 + 内层 50 次填色,校验失败直接 continue

### 9.6 帮助系统

- 问号按钮加大(22px,红色边框)
- 新增"目标分数"旁问号,弹出难度分计算公式

### 9.7 预览面板修正

- "计时并开始游戏"遮罩默认隐藏,只在载入关卡后显示
- 没有关卡时点击按钮不启动计时

### 9.8 生成结果参数显示 + 批量序列号 + Demo 动画优化

**生成结果行显示预期参数**:结果行中间空白处新增金色 chip `参数 钩30 暗钩30 暗10 5L`（`_genParams` 挂到 level，`attachGenParams` 三入口统一记录），显示的是**生成时的目标值**，与右侧灰色实际密度对比——一眼看出"想要 30% 钩子，实际 38%"。

**批量生成序列号**:状态条改为每凑到一个就推一次"已就绪 1/5（尝试 N 次）"，序列号加粗推进。

**Demo 动画三连改**（这轮核心）：
| 改动 | 问题 | 方案 |
|---|---|---|
| 棋盘不缩放 | 消除后棋盘随剩余牌包围盒放大 | `loadLevel` 记初始 `baseBounds`，渲染恒用固定边界 |
| 卡槽同尺寸 | 卡槽 56px、棋盘牌最大 80px 不统一 | `--slot-size` 变量同步成棋盘牌尺寸 |
| 飞入落槽 | 牌飞一半缩小消失 + 槽内弹出，生硬 | clone 从棋盘原位平移到卡槽中心**落进去**（挂 body + fixed 防裁剪） |
| 去槽内跳动 | 每次重渲染触发 slideIn + 重建 DOM | 删 slideIn；`renderSlots` 已有同牌不重建 |

**设计原则沉淀**:动画要做"连续"——牌从 A 到 B 应该全程可见地移动，而不是"A 消失 → B 弹出"两段式；卡槽/棋盘同一元素用同一尺寸单位，动画位移才自然。

## 十一、Day 22 新增（2026-08-18）

### 11.1 钩子定义扩展（重大改动）

**用户反馈**："万一一块麻将 A1 和另一块麻将 A2 都在底层,但是 A2 被一堆待消除的麻将压着,这怎么算呢？"

**原定义**（只看层差 ≥ 2）：
```js
if (t.layer - topLayer >= 2) buried++;
```

**问题**：同层被压、左右夹住的牌没被算作钩子。钩子数量偏少，调参数时分数波动很小。

**新定义**（任何形式的埋牌都算钩子）：
```js
function isTileBuried(tile, allTiles) {
  // 1. 同层被压：有上层牌覆盖
  const hasUpper = allTiles.some(o => 
    o.id !== tile.id && o.layer > tile.layer && 
    Math.abs(o.row - tile.row) < 2 && Math.abs(o.col - tile.col) < 2
  );
  if (hasUpper) return true;
  // 2. 左右夹：同层左右都被夹住
  const sameLayer = allTiles.filter(t => t.layer === tile.layer && t.id !== tile.id);
  const hasLeft = sameLayer.some(t => t.col === tile.col - 2 && t.row === tile.row);
  const hasRight = sameLayer.some(t => t.col === tile.col + 2 && t.row === tile.row);
  return hasLeft && hasRight;
}
```

**埋牌三种形态**：
1. **层埋**（原定义）：同一对牌中，一张在顶层、一张深埋
2. **上压**（新加）：同层一张，被上层牌压住
3. **左右夹**（新加）：同层一张，左右都被夹住（边夹住）

### 11.2 分数公式封顶调整

**原公式**：`min(effHooks / 5, 1) × 30` — 5 个有效钩子就满分，再多没意义

**新公式**：`min(effHooks / 8, 1) × 30` — 8 个有效钩子才满分，让分数有更大波动空间

**影响**：
- 钩子数 5~8 之间能拉开分数差距（之前全是封顶 30）
- 暗钩封顶 5 → 8
- 可点率、层数维度不变

### 11.3 影响评估

| 项目 | 修改前 | 修改后 |
|---|---|---|
| 钩子定义 | 只看层差 ≥ 2 | 上压/左右夹都算 |
| 钩子封顶 | 5 | 8 |
| 暗钩封顶 | 5 | 8 |
| 钩子数 | 通常 0~5 | 通常 3~15 |
| 分数波动 | 小（个位数） | 大（10+） |

### 11.4 潜在风险

- 钩子数大幅增加，可能导致大多数关卡都接近封顶
- 需要实测一批关卡，确认分布合理
- 如有必要可再次调整封顶值

## 十二、Day 23 新增（2026-08-18）

### 12.1 槽位压力维度 minSlots（解决"钩子拉满也不难"）

**用户反馈**：把钩子数量拉满也不会特别难。原版麻将有时出现"消除顺序不对就死局"——卡槽中已有的牌都被夹着或盖着，容错率暴跌。

**问题根因**：现有难度模型（钩子/可点率/层数）都是**静态指标**，只衡量开局一瞬间。真正的难点是**动态的**——消除顺序导致的连锁困境。

#### 三个候选维度分析

| 候选 | 定义 | 问题 |
|---|---|---|
| **依赖深度** | 想消最深处一对需先解多少层前置依赖 | 和"层数"高度重复 |
| **陷阱牌比例** | 开局可点牌里多少张是"点了就变难"的陷阱 | 计算量太大（每个选择都要跑解算器） |
| **最小槽位需求 minSlots** ✅ | 最优打法下卡槽最大花色占用 | 一次贪心模拟，直接对应容错率 |

#### 最终选择：minSlots

模拟聪明玩家的贪心策略，统计卡槽峰值占用：
1. 槽内已有同花色且场上能配 → 立即配对（槽位 -1）
2. 两张可点同花色 → 消掉（短暂过槽即消）
3. 只能单张 → 选"底下压牌最多"的进槽（尽早解锁）

#### 新难度公式

```
难度分 = (1-可点率)×40 + 层数×8
       + min(有效钩子/8, 1)×30
       + min(有效暗钩/8, 1)×20
       + min((minSlots-2)/4, 1)×30    ← 新增
       + 10
```

#### 生成控制：slotPressure

倒推法加 `slotPressure`（0~1）参数。倒推前中期按概率把最高层+最低层配对，正向玩时高层早露低层深埋，玩家被迫存槽。

| slotPressure | minSlots 平均 | 分数平均 |
|---|---|---|
| 0 | 1.3 | 123.5 |
| 0.5（默认） | 1.9 | 125.4 |
| 1 | 1.3 | 125.6 |

- 结果行：`钩X%/Y% · 可点Z% · 槽N/7`（≥5 加 🔥）
- 预览统计条：`槽N/7`
- 目标分数问号弹层：公式+说明更新

## 十三、Day 24 新增（2026-08-21）

### 13.1 吐牌机（Tile Spitter）

**核心机制**：吐牌机是被动供给装置——当它指向位置的牌被消除时，自动补一张新牌。

#### 数据格式

```json
{
  "tiles": [
    {"id": 1, "layer": 1, "row": -2, "col": 0, "typeId": 5, "spitterOrder": 1},
    {"id": 2, "layer": 1, "row": -2, "col": 0, "typeId": 12, "spitterOrder": 2},
    {"id": 3, "layer": 1, "row": -2, "col": 0, "typeId": 30, "spitterOrder": 3}
  ],
  "specialTiles": [
    {"id": 100, "type": "spitter", "layer": 3, "row": -2, "col": 0, "dir": "up", "count": 3}
  ]
}
```

- `tiles` 包含所有牌（包括普通牌和吐牌机队列牌）
- 队列牌通过 `spitterOrder` 标记顺序（1 最先出现，N 最后出现）
- `specialTiles` 标记吐牌机本身的位置和配置（dir + count）

#### 编辑器操作

1. 画好底座形状（常规麻将布局）
2. 选"吐牌机"画笔（⚙）
3. 点要摆吐牌机的位置 → 摆放吐牌机（橙色标记）
4. 编辑器自动在指向方向堆 N 张队列牌（N = count）
5. 配置吐牌机参数（方向 + count）
6. 点"按当前形状生成" → 系统自动填色，吐牌机队列的牌按 spitterOrder 排好

#### 关键规则

| 规则 | 说明 |
|---|---|
| 吐牌机不参与填色 | 保持橙色 ⚙ 图标，不分配 typeId |
| 吐牌机不参与配对 | 从 backwardFill 中排除 |
| 队列牌必须有支撑 | 不能悬空，否则生成时报错 |
| 偶数校验排除吐牌机 | 吐牌机本身不需要配对 |

#### 支撑限制验证

吐牌机指向的位置必须满足支撑规则（象限规则）：
- 上层牌的 4 个象限中心子格，每个正下方都必须有下层牌覆盖
- 如果队列牌悬空 → 生成时报错：`吐牌机队列牌 [L1,-2,0] 悬空无支撑`

#### 改动文件

| 文件 | 改动 |
|---|---|
| `editor/index.html` | 状态加 `stacks` 字段；吐牌机画笔自动堆队列牌；`getSpitterTarget()` 计算目标位置；渲染队列牌；导入 `spitterOrder`；`buildEditorShape` 展开队列 |
| `editor/generator.js` | `fillEditorShape` 排除吐牌机参与配对；验证支撑 + 偶数（排除吐牌机） |

### 15.1 吐牌机机制重构

**核心变化**：count 语义变更 + 队列牌参与 backwardFill 配对计算。

#### count 语义

| 旧语义 | 新语义 |
|---|---|
| count=N = 1 初始牌 + (N-1) 队列牌 | count=N = N 张队列牌 |
| 初始显示初始牌，点击后释放队列牌 | 初始显示第 1 张队列牌，点击后释放下一张 |

**示例**（count=2）：
- 初始：第 1 张队列牌（spitterOrder=1）可见
- 点击 → 进卡槽 → 第 2 张队列牌（spitterOrder=2）出现
- 点击 → 进卡槽 → 吐牌机消失

#### 队列牌参与配对计算

**问题**：之前队列牌 typeId 从普通牌池随机选，可能导致"同花色普通牌被消完了"找不到配对。

**解决**：队列牌在 backwardFill **之前**生成（typeId=null），参与配对计算，保证每张队列牌都有对应配对牌。

```
Queue tile spitterOrder=1: typeId=17 → matches normal tile typeId=17 ✓
Queue tile spitterOrder=2: typeId=31 → matches normal tile typeId=31 ✓
```

### 15.2 关键规则

| 规则 | 说明 |
|---|---|
| **吐牌机不是麻将** | 不分配 typeId，队列用尽后从棋盘消失 |
| **队列牌 typeId = 普通牌 typeId** | 参与 backwardFill 配对，可两两消除 |
| **点入卡槽立即吐下一张** | 不等配对，第 1 张进卡槽就吐第 2 张 |
| **最后一张进卡槽时 spitter 消失** | spitterOrder === count 时立即消失 |
| **L0 跳过支撑校验** | 地面就是支撑，无需校验 |
| **L1+ target 必须有支撑** | 下方有下层牌托住，否则生成报错 |
| **吐牌机不参与配对/校验** | 吐牌机本身不进 fillTiles，奇偶校验排除 |

效果：scale(0.2) → scale(1.1) → scale(1)，配合 cubic-bezier(0.34, 1.56, 0.64, 1) 缓动。

### 15.4 堆塔路径支持奇数队列牌

**问题**：`toEditorJSON` 强制让 shape 是偶数，叠加奇数 queue 后永远是奇数 → backwardFill 抛错 → 无法完成填色。

**解决**：`toEditorJSON` 新增 `skipParity` 参数；堆塔路径：队列牌总数为奇数时 `skipParity = true`，让 shape 也保持奇数。

```
奇数 shape (5) + 奇数 queue (3) = 偶数 total (8) ✓
```

## 十六、Day 27 新增（2026-08-22）

### 16.1 吐牌机队列压力维度

加入吐牌机后，原难度公式没法准确反映吐牌机带来的难度：
- 队列牌按顺序释放，玩家看到第 1 张后才能意识到"后面还有几张不知道的"
- 颜色未知，每张都得"揭开才知道"

**用户洞察（第一版）**：

> "吐牌机就是第一张牌以后的那些牌，跟暗牌几乎差不多，只不过每一张牌都约等于一个暗钩的。"

**关键等价**：每张队列牌 ≈1 个暗钩贡献难度。

**用户洞察（智能版修正）**：

> "如果吐牌机的第一张牌可以立即与牌面上的另一张普通牌进行消除，那下一张牌基本上就不算是暗钩了，因为消除这一张之后，它立刻就出来了。同理，如果第二张牌也有可消除的，那么它的第三张牌也相当于是可以直接暴露出来的。"

**关键洞察**：队列牌的"暗钩属性"取决于它前面那张能否立即消除。
- 第 1 张能消 → 不算暗钩（出牌即消）
- 第 1 张消了 → 第 2 张立即露出 → 第 2 张如果"等于可见"，也不算暗钩
- 找到第一张**无法立即配对**的队列牌，从它开始才算压力

#### 公式（智能版）

```
遍历队列牌（按 spitterOrder）：
  对第 i 张，检查它的 pair（同 typeId 的另一张牌）是否在场上且未被埋
  如果 pair 可见 → 这张牌立即可消 → 不算压力，继续下一张
  如果 pair 被埋或不存在 → 这张牌及之后所有牌都算压力

hiddenCount = 第一张不可立即配对的牌及之后的数量
spitterQueuePressure = (0.5 + hiddenCount - 1) × 8
```

| 场景 | hiddenCount | pressure |
|------|------------|----------|
| 3 张队列牌，全部 pair 都可见 | 0 | 0 |
| 3 张队列牌，前 2 张可见，第 3 张的 pair 被埋 | 1 | 4 |
| 3 张队列牌，第 1 张的 pair 就被埋 | 3 | 20 |

#### 完整公式（含新维度）

```
难度分 = (1-可点率)×40 + 层数×8 + min(有效钩子/8,1)×30
 + min(有效暗钩/8,1)×20 + min((minSlots-2)/4,1)×30
       + spitterQueuePressure + 10
```

#### 实测分数对比

测试场景：5 普通牌 + count 张队列牌（同花色配对），所有 pair都在 L0。

| 队列牌 | hiddenQueueCount | pressure | score |
|--------|-----------------|----------|-------|
| 1 | 0 | 0 | base |
| 3 | 0 | 0 | base |

所有队列牌的 pair都可见 → 不算压力。如果所有 pair都被埋，压力会线性增加。

### 16.2 设计权衡

| 选择 | 理由 |
|------|------|
| 累加 + 封顶（vs 百分制） | 每个维度上限明确，分数直接可读 |
| 约等于暗钩（vs 精确数学） | 找最相近的现有维度做类比，避免纠结精确权重 |
| 首张折半（vs 全量计算） | 1 张队列牌的关卡不应被过度惩罚；已可见/未知是合理的折半依据 |
| 智能判断（vs 全量计算） | 第 1 张能立即配对就不算压力——"出牌即消"没有认知负担 |
