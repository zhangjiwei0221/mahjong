## 一、系统总览：3 段式架构

```
浏览器（编辑器 / 工作台 / 游戏）
  │ HTTP
  ▼
Cloudflare Pages（服务器）
  │ 静态托管 + Pages Function（API）
  │ git push → 自动部署
  ▼
GitHub 仓库（数据库）
  ├── editor/  workbench.html  docs/  ...
  ├── functions/levels/[[path]].js   ← 后端 API
  └── data/levels/*.json            ← 关卡（每关一个文件）
```

**关键点**：关卡数据**不存在任何云服务的硬盘上**——全部在 GitHub 仓库的 `data/levels/` 目录里，每关一个 JSON 文件。换服务器只换"中转"，数据天然跟着仓库走。

## 二、编辑器 v4.0：浅色重构（Day 17–18）

### 解决了什么

- 原 v3.1 是通用深色游戏后台风，视觉疲劳、操作习惯不符合策划工作（弹窗 alert、缺撤销/缩放/拉伸）
- 关卡/工作台两个页面风格完全割裂（一个深色一个浅色）

### 设计选择

| 选择 | 理由 |
|---|---|
| 浅色卡片风（米白底 + 白卡片 + 赭金强调） | 策划长时间工作不刺眼，参照成熟笔记/表格类工具 |
| 红色只留给危险操作 | 解决原版"激活层=红、删除确认=红"的语义混淆 |
| 顶栏（文件/撤销/视图/帮助）+ 左侧栏卡片（图层/画笔/生成）+ 画布 + 右侧预览 | 把"创作"侧栏和"管理"侧栏分开，工作台不再挤进来 |
| 3 栏之间可左右拖拽 + 宽度记忆 | 适应不同用户的窗口习惯和内容长度 |
| 滚轮 = 缩放，空格/中键 = 平移 | 符合主流编辑器（Figma/地图）习惯，避免"上下滑扫过空白" |
| 自动保存到 localStorage | 防止误关页面丢工作 |
| 撤销/重做（Ctrl+Z/Y）、右键擦除、Delete 删单张 | 编辑器刚需，之前都没有 |

### 重点 UI 决策（基于策划反馈迭代）

- **画布收窄到牌区**：原 14 列只用了 12（牌占 -5..5），两边空白
- **默认视图填满**而非留白：避免"滚轮上下滑看到大片空白"
- **"关卡名 + 第几关"双字段**：关卡名是身份（unique），第几关是排序位；两个不同维度，都保留
- **状态（制作中/待测试/已完成）整块砍掉**：策划反馈"没必要存在"——会变成要维护的元数据，但不产生直接价值
- **作者字段砍掉**：不暴露另一个策划的人名
- **保存挪到预览面板**：生成→试玩→保存，连贯动作在同一处完成

## 三、工作台独立成页（`workbench.html`）

### 为什么独立成页，不放侧栏

- 关卡量级：**几百~上千关**（前期目标）
- 侧栏 264px 宽根本装不下"关卡名 + 序号输入 + 状态 + 统计 + 操作按钮"这种密集表格
- 独立页能用全屏宽度，渲染快、易搜索

### 功能清单

| 功能 | 实现 |
|---|---|
| 口令连接 | sessionStorage 存口令（编辑器和工作台页共享） |
| 汇总计数 | 总是显示"共 N 关 / 已排号 M / 未排号 K / 总张数 / 平均难度" |
| 搜索 | 关卡名模糊搜索 |
| 排序 | 序号 / 难度分 / 张数 / 保存时间 / 名称 |
| 筛选 | 全部 / 已排号 / 未排号 |
| 行内改序号 | 输入框 → 失焦 PATCH |
| 行内改名 | 输入框 → 失焦 PATCH |
| 下载/删除 | 按钮 → 触发 API |

### 不做（明确砍掉）

- ❌ 状态徽章（进度追踪交给 GitHub 提交记录 / 备注，不进工具）
- ❌ 作者列（不要在工具里暴露另一策划的名字）
- ❌ "加载到预览"按钮（编辑器是创作场景，工作台是管理场景，混在一起会乱）

## 四、难度公式 v2（Day 18，核心改动）

### v1 → v2 改了什么

**问题**：v1 钩子项用 `min(钩子数÷总牌数×100, 1) × 30`——百来张牌时只要 1 个钩子占比就超过 1、拿满 30 分。**钩子项退化成"有/无"开关**，1 个和 5 个钩子同分。

**改法**：`min(钩子数/5, 1) × 30`——每 1 个钩子 +6 分，5 个拿满 30。暗钩子同理。

| 项 | v1 公式 | v2 公式 | 最大 |
|---|---|---|---|
| 可点率 | `(1-可点率)×40` | 同 | 40 |
| 层数 | `层序×8` | 同 | 40（5 层时）|
| 钩子 | `min(占比,1)×30` | **`min(钩子数/5,1)×30`** | 30 |
| 暗钩子 | `min(占比,1)×20` | **`min(暗钩数/5,1)×20`** | 20 |
| 保底 | +10 | 同 | 10 |

**分母 5 怎么定的**：实测 80~110 张牌的标准关卡，钩子数观测 0~5（中位 2），5 个封顶正好覆盖。

### 实测效果

同底座 12 关（同底座，只花色/堆塔不同）：
- v1：121~127 全挤在 7 分范围
- v2：65~130 拉开 65 分，**每钩 ~10 分阶梯**（暗牌版+10，亮牌版+6）

### 已知局限（诚实记录）

- **可点率只拍开局一瞬间**——中盘难度不计入（但倒推法保证可解，不会真卡死）
- **花色种类数（typeCount）已统计但没进公式**——30 对摊在 25 种 vs 30 种难度不同，钩子只捕捉了其中层差大的部分。如果以后需要，可加"一对一花色占比"小项
- **跨模板、跨版本不可比**——绝对分只能在同系列内排序；暗/亮版不横比

### 校准闭环

这是 v2 最重要的副产品：**试玩计时**让公式第一次可证伪。流程：
1. 用 v2 生成一批新关卡
2. 实际试玩，记录通关时间 `playTimeMs`（v2 留的字段）
3. 看"分数 vs 通关时间"相关性——相关越高，公式越"诚实"
4. 调权重有据可依，不用拍脑袋

## 五、试玩计时闭环（Day 18）

```
demo 加载关卡 → 记录 startTime
    ↓
玩家试玩…
    ↓
通关（checkWin）→ 算出 durationMs → postMessage 给编辑器
    ↓
编辑器 currentLevel.playTimeMs = durationMs
    ↓
保存到工作台 → 入库 → 工作台"试玩"列显示
    ↓
后续：分数 vs 试玩时长 → 相关性分析
```

**这一循环是 v2 公式的"验收工具"**。

## 八、设计原则（沉淀）

1. **不解决"已解决"的问题**——基础功能（生成/导出/试玩）做对就够，不堆叠
2. **删除 > 添加**——砍掉的永远比加上的多：状态、作者、预览到工作台按钮、"加载到预览"……每个砍掉都让界面更清晰
3. **数据可证伪 > 拍脑袋调参**——试玩计时让难度公式第一次有反馈环路
4. **架构可移植**——后端只调 GitHub REST API，10 行代码可换任何 serverless 平台
5. **同一份逻辑多端口**——git 仓库是单一真相源，编辑器/批量工具/工作台都从同一份代码渲染
6. **少部署**——免费额度按部署烧，攒批推代码是长期省额度的核心习惯
